**结论：4/4 生成成功、身份可辨认 4/4。** 现役风格 `pixel-style-v2-animation-ready`。

## 0. ⚠️ 第一轮跑错了风格（已更正，留档）

第一轮拿 `pixel-style-v1` 跑，产物是平滑抗锯齿的伪像素风。**`pixel-style-v1` 已被淘汰。**

现役风格是 **`pixel-style-v2-animation-ready`**，依据：

| 侧 | 依据 |
| -- | -- |
| Python | `photo_avatar_backend/pixel_style.py:10` `DEFAULT_PIXEL_STYLE_ID = PIXEL_STYLE_V2_ID` |
| Rust | `creation/photo_avatar/domain.rs:9` `DEFAULT_PIXEL_STYLE_ID = PixelStyleProfileId::V2AnimationReady` |
| 真实上传入口 | `creation/photo_avatar/pixel_manager.rs:53` 传的就是 `DEFAULT_PIXEL_STYLE_ID` |
| 契约 | `pixel_contract_v2.rs` 是 current，V1 是 legacy |

根因：验收脚本里**硬编码了 `PIXEL_STYLE_V1_ID`**，而没用两侧的 `DEFAULT_PIXEL_STYLE_ID`。
已改成 `DEFAULT_PIXEL_STYLE_ID`（以后默认变了自动跟进，不会再错）。

V1 那批产物保留在 `output/L1验收/legacy-pixel-style-v1/`（`.gitignore` 覆盖，不入库），
用于对比「旧风格长什么样」。

## 1. 两个风格的实测差异（这次验收最有价值的一条）

| 维度 | V1 `pixel-style-v1`（淘汰） | V2 `pixel-style-v2-animation-ready`（现役） |
| -- | -- | -- |
| 产物尺寸 | 2048×2048 | **1024×1024** |
| 审计 schema | V1 | **V2** |
| 可见颜色 | 31，**无上限校验**（`palette_report is None` 使 Rust 的 ≤24 检查短路） | **24**，= `paletteColorLimit`，**校验生效** |
| 后处理 | 无量化 | `maxcoverage` 量化 + `box` 降采样 + `nearest` 升采样，`dither=none` |
| 抗锯齿 | 有（边缘发虚） | **无**（硬边像素块） |
| **姿态** | 一律被规范化成**正面坐姿** | **保留原照片姿态** |
| **体型** | 明显**幼化**／大头大眼 | **保留成年体型** |

第二组差异是关键：V1 把侧身站立的比格硬改成正面坐的幼犬；
**V2 的比格与金毛都保留了原图的侧身站立体型与构图**。

## 2. 覆盖范围（先说清楚没覆盖什么）

走的是**进程内直调后端两步**（`analyzeIdentity` → `generatePixelAvatar`），
真实 lk888 云端 API、真实照片、真实契约解析（`PixelStepRequest.parse`）与真实风格包。
脚本 `scripts/poc_L1真实照片验收.py`，产物与记录在 `output/L1验收/`。

**未覆盖**（不等于通过）：

- HTTP 后端（`app.py` / `uvicorn`）与 Rust `ControlledBackendProvider` 传输层；
- Rust `pixel_avatar_builder.rs` 的 schema 3 打包与 `validate_asset_directory`；
- 桌面应用内的**动态表现**（程序化呼吸 / 摇摆）——L1 判据的第二半，**仍未验收**；
- 帧序列（L2+），本次不涉及。

所以：**「L1 生成质量可用」拿到了 4/4 的证据；「端到端可安装 + 动态自然」仍未验。**

## 5. 人眼判定（权威判据，4/4 通过）

- **S1 短毛猫**：白身 + 额顶黑斑 + 黑尾三点身份特征全保留，绿眼正确。
- **S2 长毛猫**：蓬松白毛、扁脸、绿眼、**竖起的蓬松大尾**（与原图一致）。
- **S3 短毛犬**：比格三色（黑背鞍 / 黄褐 / 白）、垂耳、白鼻梁、**黑项圈**，
