# 桌面宠物项目——开发进度与计划交接文档

> 用途：跨会话开发交接。新会话先读本文件，再读各阶段计划与技术结论。

## 1. 项目概览

**目标**：Windows 优先的轻量桌面宠物（Tauri 2 + Rust + PixiJS 8），支持上传宠物照片 → 云端生成卡通形象 → 桌面陪伴（呼吸/眨眼/互动），多宠管理与离线可用。当前为**小范围测试版**阶段。

**产品定位**（已确认）：先做好"有生命感、不碍事"的桌面宠物，AI 助手/声音/主动养成为后续迭代；云端负责创造、本地负责陪伴。

**里程碑**：M0（技术探针）→ M1（P0 运行时）→ M2（P1-A 生命感）→ M3（生成链路实验）→ M4（P1-B 创建闭环）。**M0~M3 已通过，M4 自动化通过、人工闭环测试进行中**。

## 2. 技术栈与架构

- 桌面端：Tauri 2.11 + Rust + TypeScript + Vite + PixiJS 8 + SQLite（rusqlite bundled）
- 生成服务：聚合平台 lk888.ai / gpt-image-2（异步任务：submit → poll → download）
- 实验工具：`services/appearance-generation/`（Python，M3 验证用，含 rembg 抠图）
- 目录结构：`apps/desktop`（主应用）、`services/appearance-generation`（生成实验）、`scripts`、`docs`（计划/验证记录）

## 4. M4 当前状态（重要）

**已实现**：创建向导（上传照片→填 Key→生成 1 个候选→预览→编译→桌面）、任务进度轮询、单候选流程（满意/重新生成/放弃）、资产编译（manifest + 降级）、多宠切换（pet-asset 协议）、API Key 应用内配置、隐私提示。

**M4 修复链（按时间）**：
1. 透明窗口“看不到宠物”根因（布局锚点数学错误，2026-08-04 修复）：`computeAnchorPosition` 的容器偏移公式与子元素坐标系不一致——子元素按视口坐标布局，容器缩放 0.5 后应偏移 `锚点 × (1 - scale)`，原实现用了 `锚点 × (1/scale - 1)`，导致宠物整体被推到窗口下方（全局 y≈515~791，画布仅 520 高），画布实际为空。修复：修正 `computeAnchorPosition` 公式并同步修正 `getBodyBounds` 的变换；`focusable: false` 保留为创建时内置 NOACTIVATE；保留 `--disable-gpu` 基线
2. 设置/校准窗口懒创建（state 注入前不预加载）
3. 全屏检测排除桌面窗口（Win+D/点桌面不再隐藏宠物）
4. 双击弹跳不再翻转、偏移自动复位
5. 创建向导：identityMode 序列化（realPet）、任务数字 task_id 解析、轮询线程 tokio 嵌套 panic、错误可见、切页状态保持、单候选流程
6. 色键过度抠图：容差 40→12、羽化 60→6、内部洞填充恢复、最大连通域过滤背景噪点、质量报告接入任务管线（不合格降级为不透明原图）
7. 多宠切换：激活状态持久化（state 表 app:active_pet_id）+ pet-activated 事件驱动宠物窗口刷新（此前切换只改内存、窗口不重载）
8. 宠物资产加载与生成可见性：宠物窗口改用 asset_body_b64 加载（不再依赖 pet-asset:// fetch，协议响应补 CORS 兜底）；轮询补 pending→running 状态推进；缺失 API Key 的任务显式标记失败；候选页加载失败也显示操作按钮
9. 显示问题：背景均匀性检查容忍 ≤1% 边框水印/噪点（避免误判非均匀背景而整张降级成灰矩形）；抠图后按主体边界自动裁剪留 3% 边距（宠物填满窗口，不再缩在小画布中央）
10. 显示层主体感知适配：宠物窗口加载资产后计算不透明主体边界，按主体而非整张画布缩放摆放（旧资产无需重新生成也会自动变大、对齐窗口）

**M4 人工验收状态**：C-01/C-02 通过；C-03 抠图存在轻微轮廓瑕疵（MVP 接受，优化进 backlog）；C-04 状态文本正常、动态进度条未实现（低优先级）；C-05 多宠切换通过；C-06~C-10 待测。Release 复测（2026-08-05）通过——修复 release 专属 CSP 问题后，宠物显示/切宠/命中区域/动画均正常；Win10 真机兼容待测（清单见 `docs/验证记录/Win10兼容性检查清单.md`）。

- 修复眨眼调度 bug（2026-08-05）：`BlinkScheduler.nextAt` 在到期帧会先把窗口重调度到未来，导致 `now >= nextBlinkAt` 永远不成立、自动眨眼从不触发（呼吸正常、forceBlink 正常，故此前测试未覆盖）；修复为“先判定到期、再重调度”，新增自动眨眼回归测试。dev 合成闭眼层实测 14 秒捕捉到 2 次眨眼（闭眼约 120-160ms）。
- 修复“满意”按钮静默失效（2026-08-05）：`renderCandidates` 原选取**最旧**成功任务，重新生成后最旧任务的 cutout 已被编译步骤删除，候选预览失败导致 `lastJobId` 未更新，点击“满意”在 `if (!lastJobId) return` 处静默无响应。修复：候选改为**最新**成功任务；预览失败时给可见提示；按钮无任务时显示明确错误。同时把“满意”流程改为**立即编译上桌面**，不再等闭眼层（闭眼自动生成已停用，见下方说明）。
- 修复闭眼升级失败（2026-08-05）：后台升级调用 `compile_layered` 时把 `assets/body.png` 既当源又当目标，Windows 自我复制报 os error 32（文件被占用）→ 分层升级必失败。修复：body.png 已存在则跳过覆盖，只新增 eye-open/eye-closed + 更新 manifest；新增升级场景测试。真实宠物链路实测眨眼成功（14 秒捕捉 2 次闭眼）。

- 生成相似度 A/B 实测（2026-08-06）：同一张真实照片（建国2.jpg）卡通风格，A=仅参考图、B=参考图+GPT-4o 特征分析，各生成 2 张；用 GPT-4o 作裁判对每张打分（0-10）。结果 4 张全部 9 分，A/B 无可测差异——该样本特征简单（黑白花+绿眼），现有提示词+单参考图已能画准，分析未带来增量；裁判区分度也偏粗（普遍高分）。结论：单张照片场景下“更像”的瓶颈不在提示词/分析，而在**单候选的随机性**；候选数 1→2-3 让用户挑最像的一张，是当前最直接的相似度提升手段。产物：`services/appearance-generation/src/output/generation-ab/`（A-no-analysis-*、B-with-analysis-* + scores.json）。

## 5. 关键业务逻辑（M4 创建流程定稿）

```
上传+Key → 生成 1 个（进度卡片）→ 预览
  ├─ 满意，出现在桌面 → 编译（自动清理 jobs 中间产物）→ 设为当前 → 桌面
  ├─ 不满意，重新生成 → 同一宠物再生成（不重复建宠物）
  └─ 放弃 → 删除宠物记录 + 清理任务产物
```
- 切页（我的宠物/创建宠物）保持生成状态
- API Key 本地配置为**开发期方案**；SaaS 化（密钥放服务端）已记录为发布前迭代项
