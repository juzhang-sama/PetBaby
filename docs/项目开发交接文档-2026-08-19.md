## 1. 一句话结论

PetBaby 的宠物形象生成已放弃「照片 → 逐宠物 Live2D 建模」路线，改为**像素照片分身**路线：

```text
真实宠物照片
  → 像素风格身份分析（提取 15 项可辨认特征）
  → lk888 + gpt-image-2 生成一张完整、透明背景的硬边像素宠物 PNG
  → 本地规范化 + 严格机械审计
  → 用同一张 PNG 做固定整图动画（呼吸 / 轻摆 / 点击反馈）
  → 前端 Canvas 运行检查通过
  → 用户明确接受后安装到桌宠
```

Live2D 作为**技术沉淀**冻结保留，不再作为像素照片分身的生产必经路线。

## 5. 技术路线选择

### 5.1 当前主线：`pixel-style-v2-animation-ready` + `animated-image-v1`

- 风格档案：新生成默认 `styleProfileId = pixel-style-v2-animation-ready`；历史 `pixel-style-v1` 保持可读、可恢复、可按原风格再生成。
- 渲染器：`animated-image-v1`（schema v3，单张 `body.png` + `motion-profile.json` + `manifest.json`）。
- 核心视觉约束（见 `services/appearance-generation/src/photo_avatar_backend/assets/pixel-style-v2-animation-ready/`）：
  - 均衡 Q 版大头，头部约占全身高度 **38%～42%**（约 1:2.5）。
  - 紧凑坐姿、正面至轻微三分之四视角、透明背景。
  - 160 逻辑网格、最多 24 个可见色、最多 4 个身份保护色。
  - 固定 `BOX → MAXCOVERAGE → 无抖动 → NEAREST` 后处理。
  - 保留脸型、眼色、耳形、脸部花纹、胸毛、脚袜、身体斑块和尾巴。
  - 主体完整显示，不得触碰画布边缘，四周至少 4% 透明留白。

### 5.2 明确不做（禁止项）

- ❌ 极小低分辨率 sprite / 马赛克滤镜 / 平滑矢量渐变 / 写实照片复制
- ❌ 脸部贴片、身体零件拼装、语义拆层、逐宠物骨骼拟合
- ❌ Live2D 作为像素路线的静默降级或「伪成功」fallback
- ❌ 通用猫替换
- ❌ 自动切换模型、AI 分动作帧

### 5.3 Live2D 的定位（冻结的技术沉淀）

Live2D 不再进入当前像素主线，但**保留为技术沉淀与未来高级/付费路线基础**，见第 10 节。

### 5.4 继续复用的既有成果

照片上传与第三方授权、身份来源与 `user/ai-completed` 区分、任务持久化/恢复/重试/取消、重新生成、`runtimeCheckPending → previewReady → finalize` 状态链、用户显式接受后安装、照片与临时产物清理。这些都是从旧 Live2D 路线继承并被像素路线继续使用的部分，**没有推倒重来**。

## 6. 像素照片分身完整流程

### 6.1 端到端步骤（Rust 核心 + 前端 + Python 后端）

1. 用户接受第三方 AI / 照片上传告知。
2. 接收 1～8 张照片。
3. 规范化照片并写入当前 session。
4. 创建或递增 pixel revision。
5. 执行 `analyzeIdentity`（远程步骤）。
6. 生成含 15 项身份特征的 `PixelAppearanceProfileV1`。
7. 执行 `generatePixelAvatar`（远程步骤）。
8. 将原始照片和 v2 文字提示合同提交给 `gpt-image-2`；`认可参考图.png` 不作为模型图片输入。
9. 后端异步提交 → 轮询 → 下载。
10. 校验 PNG、透明通道、尺寸、哈希。
11. 写入审计元数据（新生成使用 `PixelAvatarAuditV2`；历史 v1 双读）。
12. 生成运行包：`body.png` + `motion-profile.json` + `manifest.json`（schema v3）。
13. 前端创建真实 Canvas 预览（`animated-image-v1`）。
14. 检查可见像素与动作变化。
15. 运行检查通过后进入 `previewReady`。
16. 用户明确接受后才安装并切换为当前桌宠。

### 6.2 状态机（`PixelPhotoAvatarStep`，共 10 态）

```text
Collecting → AnalyzeIdentity → GeneratePixelAvatar → QualityCheckPending
  → RuntimeCheckPending → PreviewReady → CleanupPending → Completed
```
异常分支：`Failed`、`Cancelled`。

- 每个远程步骤最多 3 次尝试。
- 轮询必须继续查询**同一个 provider task**，不得因暂时性轮询错误重复提交新任务。

## 7. 动画实现（整图固定动作）

核心文件：`apps/desktop/src/runtime/animated-image-renderer.ts`、`animated-image-motion.ts`。

固定生命感参数（`LIFE_V1`）：

| 参数 | 值 |
|---|---|
| 呼吸周期 `breathPeriodMs` | 2800ms |
| 呼吸横向缩放 `breathScaleX` | 2.8% |
| 呼吸纵向位移 `breathShiftY` | 1.2% |

## 8. 前端运行检查门槛（关键放行门）

文件：`apps/desktop/src/settings/photo-avatar-pixel-preview.ts`

```ts
if (neutralPixels <= 0 || changedPixels <= 20) {
  throw new Error("像素预览运行检查未检测到有效图像或动作变化");
}
```

- `neutralPixels`：静态帧可见像素数，必须 > 0（Canvas 确实画出了图）。
- `changedPixels`：两帧之间变化像素数，必须 > 20（动作确实产生了可见变化）。
- 检查不通过则**不得进入 `previewReady`**，不得安装。
- 历史上出现过「容器尺寸为 0 → Canvas 初始化为 1×1 → 永远测不到变化」的问题（见第 11 节），检查时必须保证预览容器已可见且有非零尺寸。

## 9. 三层轮询（容易混淆，务必区分）

| 层 | 文件 | 间隔 | 目标 |
|---|---|---|---|
| 前端 | `settings/photo-avatar-creation-view.ts` | 1000ms | 轮询本地后端 job 状态 |
| Rust 桌面端 | `creation/photo_avatar/pixel_remote.rs` | 250ms | 轮询本地后端 job 状态 |
| Python 后端 | `photo_avatar_backend/pixel_avatar.py` | 60s | 轮询 lk888 provider 生成任务 |

后端对 lk888 的轮询：`poll_interval_seconds = 60.0`，`max_wait_seconds = 300.0`（总超时 5 分钟）。前端/Rust 的短间隔是针对**本地后端**的，与 provider 生成耗时无关；不要把三层混为一谈。

## 11. 历史故障与修复（图片回传失败的四个根因）

上一轮开发中，用户反复遇到「lk888 后台已生成图片，但前端一直提示生成失败」。经系统排查，根因有四个，均已修复：

| # | 根因 | 修复 | 关键提交 |
|---|---|---|---|
| 1 | 首次打开创建页自动恢复旧 `failed` 会话（草稿未 abandon） | 恢复 `failed/cancelled` 时自动 abandon 旧 session 并新建；取消时按 `cancel → abandon → 返回首页` 顺序执行 | `fa02290` |
| 2 | 「取消创建」只调了 cancel，没 abandon 整个创建草稿 | 同上，补 `creation.abandon` | `fa02290` |
| 3 | 取消后迟到的后台线程仍把状态覆盖成 `failed`（竞态） | 新增 `fail_pixel_revision_if_active`，SQL 只允许非终态同 revision 转 failed | `adef7d5` |
| 4 | lk888 成功返回图，但本地 PNG 审计拒绝（主体触边，alpha margin < 2%），被误判为可重试 provider 故障，导致重复生成 3 张 | 新增 `normalize_pixel_png()`：裁主体→等比缩到 92%→NEAREST→alpha 二值化→透明 RGB 清零→居中→再审计；并在提示词合同加「不触边、四周 4% 留白」 | `6fc7eda` |

**轮询关键修复**（`pixel_avatar.py`）：

原逻辑 `if state.is_final: break` 会在 provider 暂态返回 `cancelled/failed + is_final=True` 时提前失败，随后 Rust 重提新 task，造成「后台有图、前端失败、重复生成」。已改为：

```python
if state.state == "success" and state.result_url:
    break
```

非成功状态继续轮询同一 task，直到 300s 超时。

**PNG 机械门**（`pixel_png.py` / `pixel_audit.py`，勿随意放宽）：

- 只接受 RGBA PNG；每边 1024～2048；总像素 ≤ 4,194,304。
- 四边 alpha margin ≥ 2%；partial alpha ≤ 2%；最大 8 邻接主体 ≥ 95%。
- 透明像素 RGB 归零规范化。
- v2 固定 160 逻辑网格，可见色数 ≤ 24，保护色数 0～4；Rust 运行包构建器独立重算可见色数并绑定 audit。

### 13.1 开发硬约束（浮点契约纪律，必须遵守）

**凡是跨语言（Python ↔ Rust）或跨精度（f64 ↔ f32）的数值契约，二选一：只在一端算（另一端只传递不重算），或比较必加容差（f64 用 1e-9、f32 用 1e-5），禁止对浮点做 `==`/`!=`/`<`/`>` 精确比较。**

已踩过的三个坑（务必警惕）：
- **sha256 契约不同步**：改资产（风格档案.json / 认可参考图.png / 提示词合同.md）忘同步 Rust 硬编码哈希 → `validate_success` 静默失败。
- **f64 1 ULP**：Python `int/int` vs Rust `f64/f64` 算同一个 ratio，差 1 ULP → bit 级比较失败。
- **f64→f32 1 ULP**：write_preview 用 f64 算、validate 用 f32 重算 face_safety_line，差 1 ULP → `<` 边界误判。

硬编码哈希/版本常量：改对应资产必须同步常量，并在常量旁注释说明同步方法。
