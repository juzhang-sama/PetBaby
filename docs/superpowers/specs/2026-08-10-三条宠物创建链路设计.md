# 三条宠物创建链路设计

## 1. 文档状态

- 日期：2026-08-10
- 状态：设计已确认，等待实施计划
- 适用版本：本地 MVP 第一版
- 物种范围：仅猫
- 前置规格：
  - `2026-08-10-宠物管理与创建闭环设计.md`
  - `2026-08-10-全宠物基础动态设计.md`

## 2. 背景与目标

当前产品已经具备“上传图片生成宠物”的单候选链路，并已打通动态预览、运行时编译、桌面热切换、当前宠物持久化、目录管理和安全删除。新建的图片宠物会在生成过程中获得呼吸与微动能力，不需要用户额外配置。

本阶段要把创建入口扩展为三条正式产品链路：

1. **上传图片**：用户上传已有宠物照片，系统生成宠物形象。
2. **引导组合**：用户从固定的猫咪部件中逐步选择，所见即所得地组合宠物。
3. **直接认领**：用户从系统内置的成品猫目录中选择并认领。

三条链路的来源不同，但完成后必须得到同一种用户宠物：可立即出现在桌面、具备呼吸与微动、可切换、可恢复、可删除，并由统一目录展示。

本设计的核心目标是建立一个统一创建领域，让上传、组合和认领成为三个来源适配器，而不是三套彼此独立的创建系统。

## 3. 已确认的产品原则

### 3.1 统一完成标准

- 所有新宠物在进入可用状态前必须已经具备呼吸和微动。
- 用户不需要感知动作配置、编译器或渲染器类型。
- 只有文件安装、桌面显示、数据库持久化和会话完成全部成功后，界面才能提示创建成功。
- 三种来源的宠物进入“我的宠物”后拥有相同的切换和删除能力。
- 宠物来源只用于展示、追溯和恢复，不改变日常使用能力。

### 3.2 第一版范围

- 只支持猫。
- 采用统一的“可爱半写实桌面宠物”美术风格。
- 引导组合不经过 AI 二次融合，使用分层所见即所得合成。
- 引导组合只保留一个长期未完成草稿。
- 认领目录完全离线，随应用发布。
- 认领实例可以删除，系统原始成品包始终保留。
- 同一个内置模板同时最多存在一个用户认领实例；删除后可以再次认领。
- 上传和组合在最终确认前要求命名；认领提供默认名字并允许确认前修改。
- 不同宠物允许使用相同显示名称，内部身份始终使用唯一 `petId`。

### 3.3 第一版不包含

- 猫以外的动物。
- AI 二次融合或 AI 部件修补。
- 衣服、帽子、项圈等装饰维度。
- 创建完成后的重新编辑和重命名。
- 眨眼、嘴部、耳朵、尾巴或肢体动作。
- 远程素材商店、在线模板更新、账号、云同步和跨设备同步。
- 同时保存多个上传或组合草稿。
- 将认领模板直接作为用户宠物运行时资源长期引用。

## 4. 方案选择

### 4.1 采用方案：统一创建领域加三个来源适配器

系统建立一个共享的创建会话、标准候选和完成协调器：

- 上传适配器把生成任务转换为标准候选。
- 组合适配器把本地分层配方转换为标准候选。
- 认领适配器把内置模板实例化为标准候选。
- 共享流程负责命名、动态预览、编译、安装、热切换、持久化和完成。

该方案最大限度复用现有动态资源、运行时编译和两阶段热切换能力。后续新增创建来源时，只需实现新的来源适配器，不需要复制完成事务。

### 4.2 未采用方案

**直接引用共享认领模板**没有采用。它可以减少磁盘复制，但会让用户名称、`petId`、资源版本、删除语义和应用升级耦合到系统模板，增加运行时清单与版本迁移复杂度。

**三条独立流水线**没有采用。它短期改动直观，但会重复草稿恢复、命名、动态预览、安装、热切换、删除和错误处理，长期容易产生不一致。

## 5. 用户入口与业务流程

### 5.1 统一入口

设置页的“创建新宠物”展示三个入口卡片：

- 上传图片：文案“我有一张宠物照片”。
- 引导组合：文案“我想亲手组合一只猫”。
- 直接认领：文案“我想马上拥有一只猫”。

上传与引导组合共享一个长期草稿槽。若已经存在未完成草稿，再次进入上传或组合时必须让用户选择继续当前草稿或放弃后重新开始。认领浏览不会覆盖该草稿。

### 5.2 上传图片

流程为：

`选择照片 → 生成形象 → 动态候选预览 → 输入名称 → 满意并显示在桌面`

现有上传生成、候选、动态配置和编译能力继续使用，但会接入统一创建会话和完成协调器。上传提供方失败时保留原图、任务事实及已成功产生的候选，允许重试或放弃。

### 5.3 引导组合

流程为：

`身体底型 → 耳朵 → 眼睛 → 鼻嘴表情 → 尾巴 → 毛色与花纹 → 输入名称 → 动态预览 → 满意并显示在桌面`

规则如下：

- 用户选中第一个身体底型后立即创建并保存草稿。
- 每次选择自动保存，关闭设置页或应用后可以继续。
- 用户可以返回任意已完成步骤并重新选择。
- 预览使用与最终导出相同的合成器，保证所见即所得。
- 草稿不进入“我的宠物”，也不会显示在桌面。
- 创建完成后第一版不允许重新进入编辑器，但组合配方永久保留。

### 5.4 直接认领

流程为：

`浏览 8 只成品猫 → 查看动态预览和介绍 → 保留或修改名称 → 确认认领 → 显示在桌面`

规则如下：

- 认领目录读取应用内置只读资源，不依赖网络。
- 未认领模板显示“认领”。
- 已认领模板显示“已认领”，并允许直接切换到对应用户宠物。
- 删除认领实例后，模板恢复为可认领。
- 认领确认前不占用长期草稿槽；确认后建立短期安装会话。

## 6. 统一领域模型

### 6.1 用户宠物

用户宠物在现有身份和运行时数据上增加以下领域属性：

- `petId`：稳定唯一身份，也是目录和运行时关联键。
- `displayName`：用户可见名称。
- `species`：第一版固定为 `cat`。
- `creationMethod`：`upload | composer | adoption`。
- `sourceTemplateId`：仅认领实例填写。
- `sourceTemplateVersion`：仅认领实例填写。
- `createdAt`：完成创建的时间。

名称不参与路径拼接、资源定位、唯一性判断或切换。认领实例通过 `sourceTemplateId` 的部分唯一约束保证同一模板最多存在一个有效用户实例。

现有用户宠物迁移时保留已有目录显示名称；没有名称的记录统一回填为“我的猫咪”。因为重复显示名称合法，该回填不需要生成序号，也不会改变 `petId`。系统默认 Live2D 猫继续使用现有固定名称，不进入用户名称迁移。

创建会话建立时就预留 `petId`。同一数据库事务可以建立现有生成外键所需的内部身份记录，但该记录仅是创建事实，不得投影为正式目录项；只有生命周期达到 `ready` 后才进入“我的宠物”。放弃时精确清理该创建会话拥有的身份和资源。

### 6.2 创建会话

统一创建会话至少记录：

- `sessionId`。
- 预留的 `petId`。
- 创建方式。
- 当前状态与当前步骤。
- 最近一次可安全恢复的状态。
- 创建、更新时间和完成时间。
- 会话结构版本。
- 是否已放弃。

方法专属数据保持独立所有权：

- 上传会话关联现有 `generationJobId`。
- 组合会话关联一份组合配方。
- 认领会话关联 `sourceTemplateId` 和模板版本。

上传和组合只允许存在一个未完成的长期会话。认领确认产生的短期会话不覆盖长期草稿。

“最多一个长期草稿”既由领域服务检查，也由数据库约束保护；并发进入上传和组合不能各自创建一个未完成会话。

### 6.3 会话状态机

统一状态为：

`draft → candidateReady → finalizing → completed`

还允许两个终止或恢复状态：

- `retryableFailure`：保留最近的安全产物，可以重试。
- `abandoned`：用户明确放弃，关联临时资源已清理。

状态转换由后端领域服务控制，前端不能通过本地内存直接宣告完成。完成请求必须幂等：相同 `sessionId` 重试时返回同一个结果，不创建新宠物。

进入 `retryableFailure` 时必须保留最近一次可安全恢复的状态。重试根据该状态回到 `draft` 或 `candidateReady`，不能盲目从头执行。`abandoned` 和 `completed` 都是终态。

### 6.4 标准外观候选

三条来源最终都产出同一候选契约：

- 候选 ID、所属创建会话和预留 `petId`。
- 透明主体图。
- 动作语义与 `motion-profile`。
- 来源及可追溯元数据。
- 文件角色、相对路径和哈希。
- 必要的分层或部件语义元数据。
- 候选结构版本和创建时间。

现有 `appearance_variants` 应改为以创建会话作为通用所有者。`generationJobId` 仅对上传来源存在，不再是所有候选的必填前提。旧上传记录通过迁移建立对应创建会话，不丢失既有生成事实。

## 7. 引导组合素材契约

### 7.1 素材包版本

每个组合素材包具有不可变的 `packId + packVersion`。发布后的同一版本不得原地替换内容。组合配方固定引用创建时的版本，素材包升级不会改变已经创建的宠物。

第一版使用一个统一风格猫咪素材包，最低内容数量为：

- 3 个身体底型，身体包含脸型、躯干和四肢。
- 4 套耳朵。
- 5 套眼睛，每套同时包含睁眼和闭眼状态。
- 4 套鼻子、嘴巴和表情组合。
- 4 条尾巴。
- 6 种基础毛色。
- 4 种花纹遮罩，以及一个无花纹选项。

以上数量是可发布内容的最低要求，测试夹具不能替代正式素材。

### 7.2 画布与图层

- 素材使用统一逻辑坐标系和透明 RGBA 画布。
- 正式导出分辨率固定为 1024×1024。
- 桌面运行时继续按现有 contain 规则缩放，不改变窗口尺寸协议。
- 默认可见层顺序为：后置尾巴、身体底型、耳朵、眼睛、鼻嘴表情。
- 素材清单可以在固定图层组内部指定稳定排序，但用户不能任意改变层级。

每个部件条目至少包含：

- 稳定部件 ID、类别和资源路径。
- 锚点、逻辑尺寸、图层组和顺序。
- 可见区域与透明边界。
- 可选的着色遮罩和花纹遮罩。
- 兼容标签与排除规则。
- 与未来动作相关的语义标识。

系统只向用户展示与当前身体底型及已有选择兼容的部件。兼容性在选择前过滤，不能等到最终导出时报错。每个身体底型都必须存在一套完整默认选择，确保用户始终可以走完流程。

### 7.3 毛色与花纹

毛色通过素材作者提供的着色遮罩应用，不直接覆盖原始阴影、高光和轮廓。花纹通过部件的花纹遮罩裁切，不能溢出身体、耳朵或尾巴轮廓。毛色和花纹是绘制各部件时执行的样式操作，不是独立覆盖在所有部件之上的单一图层。

“无花纹”是显式配方值，不用缺失字段表示。所有颜色值来自素材包清单，第一版不提供自由取色器。

### 7.4 确定性合成

组合器是纯本地确定性组件，不调用网络或 AI：

1. 读取已固定版本的素材包清单。
2. 按配方选择部件并校验兼容性。
3. 按固定图层、锚点和遮罩绘制预览。
4. 使用同一渲染核心导出 1024×1024 透明 PNG。
5. 输出组合配方、动作语义和文件哈希。

相同素材包版本和相同配方必须产生相同像素结果。编辑器预览与最终导出共用渲染核心，不允许分别实现两套合成规则。

### 7.5 组合配方

配方是组合宠物的权威来源，至少包含：

- 配方版本。
- 素材包 ID 和版本。
- 身体、耳朵、眼睛、鼻嘴表情和尾巴部件 ID。
- 基础毛色 ID。
- 花纹 ID。
- 图层与锚点契约版本。

完成后配方只读保存。第一版不提供重新编辑入口，但不得丢弃配方，也不得只保留扁平 PNG。

### 7.6 动作语义与未来扩展

组合素材包必须提供：

- 面部安全区。
- 胸腹呼吸区。
- 整体微动支点。
- 睁眼与闭眼资源对应关系。
- 耳朵和尾巴语义部件标识。

第一版只把面部安全区、呼吸区和微动支点写入当前动态配置。闭眼、耳朵和尾巴语义保留但不激活动作。未来增加眨眼、耳动和尾动时，可以基于已保存配方和状态资源升级，而不要求用户重新创建宠物。

### 7.7 素材包校验

应用构建或测试阶段必须校验：

- 清单结构和版本受支持。
- 所有 ID 唯一且引用存在。
- 图片尺寸、透明通道和边界合法。
- 锚点、遮罩和动作区域位于画布范围内。
- 每套眼睛同时存在睁眼和闭眼状态。
- 每个身体底型具有完整默认组合。
- 所有可展示组合路径都能生成有效透明结果。
- 文件哈希与清单一致。

单个损坏部件在运行时只禁用该部件；若素材包无法提供任何完整默认组合，则整个引导组合入口不可用并显示明确原因。

## 8. 认领目录与模板契约

### 8.1 内置目录

第一版随应用提供 8 个可认领成品猫模板。每个模板至少包含：

- 稳定的 `templateId` 和递增的 `templateVersion`。
- 默认名称和简短性格介绍。
- 目录缩略图。
- 与桌面一致的动态预览资源。
- 已编译透明主体图、动作配置和运行时清单。
- 文件哈希和最低兼容版本。

8 个模板必须在外观、默认名称和介绍上可区分，并全部具备呼吸与微动。系统默认 Live2D 猫是不可删除的安全回退项，不属于这 8 个可认领模板。

### 8.2 只读模板与用户实例

系统模板位于应用只读资源中，不能被删除服务、用户目录清理或认领操作修改。认领时不能让用户宠物长期直接引用共享模板，而要执行实例化安装：

1. 生成新的 `petId` 和 `sessionId`。
2. 将模板复制到唯一临时目录。
3. 写入用户确认的名称、来源模板 ID 和模板版本。
4. 重写需要用户身份的运行时字段并重新计算哈希。
5. 校验后原子安装为独立用户资源。
6. 通过统一完成协调器切换并提交。

删除认领实例只删除用户资源和用户记录。系统模板始终保留。应用升级后的模板新版本不会改变已认领实例；删除后再次认领时使用当前应用内置版本。

### 8.3 认领状态

模板是否已认领由持久化用户宠物事实投影得到，不由前端缓存决定。数据库对有效用户宠物的 `sourceTemplateId` 建立唯一约束。

- 模板未被认领时显示“认领”。
- 模板已被认领时显示“已认领”，并关联到对应用户宠物。
- 删除实例并提交成功后，该模板恢复可认领。
- 安装、切换或持久化失败时，不占用认领资格。

## 9. 统一命名规则

- 按 Unicode 空白规则去除首尾空白后，名称长度为 1～20 个 Unicode 字素簇，即用户感知字符。
- 允许任意可见 Unicode 字符和名称内部的普通空白。
- 禁止换行符、行分隔符、控制字符和纯空白名称。
- 允许不同宠物使用相同显示名称。
- 名称只作为显示信息，不参与文件路径和内部身份。
- 上传和组合必须在最终确认前输入名称。
- 认领默认填入模板名称，用户可以保留或修改。
- 第一版完成后不提供重命名。

## 10. 共享完成协调器

### 10.1 标准流程

三条来源进入统一候选契约后执行：

`候选校验 → 动态预览 → 名称确认 → 运行时编译 → 临时安装 → 桌面热切换 → 持久化 → 完成`

不同页面可以在名称确认前先展示预览，但不得绕过任何完成门槛。上传和组合候选使用当前 `animated-image-v1` 运行时；认领模板也必须提供同一可用运行时契约。`static-png` 不能作为正式完成态。

### 10.2 成功条件

创建成功必须同时满足：

1. 透明图、动作配置、运行时清单和哈希全部有效。
2. 独立用户目录已经原子安装。
3. 桌面窗口成功加载、探测并显示新宠物。
4. 数据库已经记录正式用户宠物、来源和当前宠物。
5. 当前宠物会话与持久化 ID 一致。
6. 创建会话已经标记为 `completed`。

任何较早阶段都不能显示“宠物已经出现在桌面”。

### 10.3 两阶段热切换与提交

完成协调器复用现有两阶段热切换：

1. 在唯一临时目录编译并校验候选。
2. 原子安装用户资源，但尚不宣告完成。
3. 桌面窗口准备独立候选运行时，完成资源加载与首个非空帧探测。
4. 激活候选并保留旧运行时作为回滚目标。
5. 在数据库事务中提交宠物正式状态、来源、当前 ID 和会话完成事实。
6. 提交桌面运行时交换，销毁旧候选宿主。
7. 刷新目录并向同一请求返回成功。

失败补偿规则：

- 准备或探测失败：销毁候选运行时，旧宠物不变。
- 激活后数据库失败：桌面回滚到旧宠物，清理不完整正式目录，候选回到可重试状态。
- 最终清理失败：宠物业务提交保持成功，记录可重试的残留清理警告，不能伪造业务失败后重复创建。
- 前端未收到成功响应：相同会话重试时返回已经完成的同一宠物。

## 11. 草稿、恢复与放弃

### 11.1 自动保存

组合草稿从首次选择身体底型开始持久化。每次有效选择更新配方和当前步骤；保存失败时界面必须保留本地当前选择并提示未保存，不能假装可以安全关闭。

应用或设置页重新打开时，从持久化会话和配方恢复，而不是恢复一个前端页面快照。

### 11.2 启动恢复

应用启动时协调器检查所有非终态会话：

- `draft`：恢复到对应上传或组合页面。
- `candidateReady`：恢复到预览、命名或完成确认。
- `finalizing`：核对用户目录、数据库、当前 ID 和桌面可恢复状态。
- 已完整提交但未回写响应：补记 `completed`。
- 未完整提交：清理孤儿安装并回到 `retryableFailure`。

恢复必须幂等，多次启动不能重复安装、重复认领或重复删除。

### 11.3 放弃

用户放弃上传或组合草稿时：

- 精确删除该会话拥有的临时候选、编译产物和生成任务资源。
- 删除仅为该草稿预留的内部宠物身份。
- 不影响任何正式用户宠物、当前宠物或系统模板。
- 复用现有安全删除与隔离清理能力，不通过宽泛目录扫描删除文件。

## 12. 并发与一致性

### 12.1 三层防重

1. 前端在完成、切换或删除期间进入明确忙碌状态，禁用重复操作。
2. 后端以 `sessionId` 和请求 ID 保证完成请求幂等。
3. 后端使用统一宠物变更锁，串行协调创建完成、当前宠物切换和删除。

数据库唯一约束独立保证认领模板不会产生两个有效实例。前端按钮状态不是一致性的最后防线。

### 12.2 页面并发

所有目录、预览和向导异步请求绑定页面访问序号。用户返回、关闭页面或进入另一条链路后，旧请求结果不得覆盖当前页面；过期请求只能释放自己创建的资源。

### 12.3 与删除的互斥

- 创建完成、普通切换和删除不能同时修改当前宠物。
- 删除服务提交前必须重读当前宠物，防止删除正在被设为当前的目标。
- 删除当前用户宠物时，先通过同一热切换协调器切回不可删除的系统默认猫，再执行删除。
- 认领实例删除成功后，目录投影才释放对应模板资格。

## 13. 错误处理与安全边界

### 13.1 局部失败

- 某个组合部件损坏：禁用该部件，不阻断其他有效组合。
- 某个认领模板损坏：禁用该模板，不阻断其他模板。
- 素材包整体无法形成完整默认组合：禁用引导组合入口并显示原因。
- 上传提供方不可用：保留草稿和已成功产物，允许重试。
- 桌面窗口无响应：不提交新宠物，旧宠物继续运行。

### 13.2 资源安全

- 所有素材包、模板、部件、会话和宠物 ID 都按严格格式校验。
- 资源 ID 是逻辑标识，不能直接作为未经校验的磁盘路径。
- 相对路径必须限制在对应素材包、模板、会话或宠物根目录内。
- 拒绝绝对路径、父目录遍历、编码分隔符和清单外文件。
- 清单解析后再验证文件角色、哈希、图片类型和透明通道。

### 13.3 用户错误文案

用户界面显示可执行的中文信息，例如：

- “草稿没有保存成功，请重试后再关闭。”
- “这个部件暂时不可用，请选择其他部件。”
- “宠物窗口没有响应，原来的宠物仍在桌面上。”
- “认领没有完成，你可以重新尝试。”

底层日志保留 `sessionId`、`requestId`、`petId`、来源、失败阶段和原始错误链。

## 15. 完成标准

- 三个创建入口在设置页正式可用。
- 上传链路迁入统一创建领域且既有能力无回归。
- 引导组合拥有正式猫咪素材、可恢复草稿、所见即所得导出和动态完成链路。

- 三条链路都只能产出具备呼吸和微动的可用宠物。
- 所有成功提示都发生在桌面显示与持久化真正成功之后。
- 自动化测试、内容契约测试和真实 Tauri 验收均有结果记录。

## 16. 实施分解原则

本规格是一个完整产品能力，但实施计划必须分阶段交付并保持主干可运行：

1. 统一创建会话、来源字段、候选所有权和命名规则。
2. 组合素材契约、确定性合成器、配方和草稿恢复。
3. 认领目录、模板校验、实例化安装和唯一认领。
4. 三入口界面与统一完成协调器接入。
5. 内容补全、跨链路回归和真实桌面验收。

每个阶段都必须保持现有上传、宠物目录、热切换、删除和默认 Live2D 猫可用。实施计划不得把正式美术素材替换成永久占位图，也不得为了赶进度把动态资源降级为静态完成态。
