# Windows 一键启动与编译边界设计

日期：2026-08-11

## 1. 背景与目标

PetBaby 当前通过 `apps/desktop` 下的 `npm run tauri dev` 启动。Tauri 会启动 Vite 开发服务器、编译并运行 Rust 桌面端，但使用者仍需手动进入目录、安装依赖并确认 Cubism SDK 已准备完成。

本轮开发提供一个从仓库根目录双击即可使用的 Windows 开发启动入口，同时盘点并冻结现有 Windows 原生代码边界。完成后进入第一轮人工测试，通过实际使用寻找缺陷，再决定是否开发新功能。

本轮目标：

- 在仓库根目录提供可双击的一键启动文件。
- 缺少 npm 依赖时自动安装。
- 缺少 Cubism 开发资源时只在 `CUBISM_SDK_ROOT` 已配置的情况下自动准备，否则明确失败。
- 使用一个 Tauri 命令统一启动 Vite 前端、Rust 后端和桌宠进程。
- 增加静态契约，防止启动行为和 Windows 原生代码边界意外漂移。
- 在 Windows 上执行编译检查，只修复本轮核验实际发现的纯编译问题。

## 2. 非目标

本轮不包括：

- 开发或验证 Linux、macOS 等其他操作系统。
- 启用 MSI、NSIS 或其他正式安装包。
- 修改正式 `creation-content`、Live2D 模型或 Task15 验收证据。
- 调用真实 provider、读取 API Key 或删除宠物及创建草稿。
- 重构现有候选发布、认领和 motion profile 的 Windows 文件安全协议。
- 修改或删除 `.worktrees/breath-sway-runtime`。
- 执行发布态内存专项优化；内存测试属于完成启动能力后的第一轮测试内容。

## 3. 运行形态

开发态不是独立部署的前端服务器和后端服务器。`npm run tauri -- dev` 负责统一编排：

1. Tauri CLI 根据 `beforeDevCommand` 启动 Vite。
2. Cargo 编译并运行 Rust 桌面程序。
3. `desktop-pet.exe` 通过 WebView2 加载 Vite 页面。
4. 退出 Tauri 开发进程时，其管理的 Vite 子进程一并结束。

正式发布后，前端静态资源应随桌面程序分发，最终用户不需要 Node、Vite、Cargo、Cubism SDK 或 `CUBISM_SDK_ROOT`。正式发布预检和安装包配置不属于本轮范围。

## 4. 启动器架构

### 4.1 双击入口

仓库根目录新增 `一键启动桌宠开发环境.cmd`。该文件只负责：

- 使用 `%~dp0` 定位仓库根目录；
- 通过 `powershell.exe -NoProfile -ExecutionPolicy Bypass` 调用启动脚本；
- 返回 PowerShell 脚本的退出码；
- 失败时保留窗口，让用户能够阅读错误信息。

批处理文件不承载依赖判断和启动业务逻辑，避免难以测试的命令行分支。其文件名保留中文，但文件内容必须只包含 ASCII 字节，并调用 ASCII 路径 `scripts/start-desktop-pet-dev.ps1`，避免 CP936 将无 BOM UTF-8 中文路径解析为乱码。

### 4.2 PowerShell 编排脚本

`scripts/start-desktop-pet-dev.ps1` 负责实际编排。脚本必须以 `$PSScriptRoot` 解析仓库和 `apps/desktop` 目录，不能依赖调用者的当前目录；源码使用带 BOM 的 UTF-8，使 Windows PowerShell 5.1 能正确读取中文诊断。

执行顺序固定为：

1. 检查 `npm` 和 `cargo` 是否可执行。
2. 在 `apps/desktop` 执行 `npm ls --depth=0 --silent`，并检查 `node_modules/.bin/tauri.cmd`。
3. npm 依赖树或本地 Tauri CLI 不完整时执行 `npm install`；安装后重新验证两项后置条件，仍不完整则返回保留错误码 `13`。
4. 检查以下 Cubism 文件：
   - `.vendor/live2d-cubism-sdk/Core/live2dcubismcore.min.js`
   - `.vendor/live2d-cubism-sdk/Framework/src/live2dcubismframework.ts`
   - `public/live2d/Core/live2dcubismcore.min.js`
5. 任一 Cubism 文件缺失且 `CUBISM_SDK_ROOT` 非空时，执行 `npm run prepare:cubism`，然后重新检查三个文件。
6. Cubism 仍缺失时输出中文错误并返回非零退出码，不允许使用不可用运行时继续测试。
7. 执行 `npm run tauri -- dev`，直接继承控制台输入输出。
8. 将依赖安装、SDK 准备或 Tauri 启动的失败码返回给调用者。

脚本不得启动第二套手工管理的 Vite 进程，因为 `tauri.conf.json` 的 `beforeDevCommand` 已是唯一前端启动所有者。

### 4.3 错误信息

错误提示使用中文，并明确下一步：

- 缺少 npm：提示安装 Node.js/npm。
- 缺少 cargo：提示安装 Rust 工具链。
- `npm install` 失败：保留 npm 原始输出和退出码。
- npm 安装后仍不完整：以中文提示依赖树或本地 Tauri CLI 后置条件失败并返回保留错误码 `13`。
- Cubism 缺失：提示设置 `CUBISM_SDK_ROOT` 为官方 Cubism SDK for Web 根目录。
- Tauri 启动失败：保留 Tauri/Cargo/Vite 原始输出。

启动器不捕获、隐藏或改写底层命令的详细错误。

## 5. Windows 原生代码边界

项目协作约束要求 Windows 专属代码集中在 `src-tauri/src/platform/windows.rs`。当前安全发布和文件身份协议已经在以下文件中存在经验证的 Windows 专属实现：

- `src-tauri/src/platform/windows.rs`
- `src-tauri/src/creation/candidate.rs`
- `src-tauri/src/creation/adoption.rs`
- `src-tauri/src/runtime_assets/motion_profile.rs`

后三处属于既有安全协议债务，本轮不做高风险搬迁。静态契约以显式允许清单冻结现状：

- 禁止新的 Rust 文件直接引入 `std::os::windows`、`windows_sys`、`windows::Win32`、`winapi::`、`raw_window_handle::Win32`、`extern "system"`、`#[link(`、Win32 类型或裸句柄。
- 允许清单中的新增直接 Windows API 使用仍需对应测试，并应优先下沉到 `platform/windows.rs`。
- 本轮若 `cargo check` 发现纯编译错误，只做不改变文件安全、发布和恢复语义的最小修复。

该契约用于阻止边界继续扩散，不代表现有例外已经达到最终架构目标。

## 6. 测试设计

### 6.1 启动脚本静态契约

新增 Vitest 契约测试，读取实际 `.cmd` 和 `.ps1` 文件并验证：

- 双击入口内容只含 ASCII，并通过 `%~dp0` 定位 `scripts/start-desktop-pet-dev.ps1`。
- PowerShell 通过 `$PSScriptRoot` 定位项目。
- 依赖完整性通过 `npm ls --depth=0 --silent` 判断；缺失分支执行 `npm install` 并重新验证依赖树和本地 Tauri CLI。
- Cubism 检查同时覆盖 vendor Core、vendor Framework entry 和应用实际加载的 public Core。
- SDK 自动准备必须受 `CUBISM_SDK_ROOT` 控制。
- SDK 仍缺失时返回失败，而不是继续启动。
- Tauri 启动命令为 `npm run tauri -- dev`。
- 启动器不包含 `Remove-Item`/删除命令、HTTP/网络调用、provider、API Key、宠物或草稿删除命令，也不引用正式 `creation-content` 路径。

除静态断言外，测试通过 Windows PowerShell 子进程、临时 desktop root 和临时 `.cmd` 替身实测保留退出码 `10`、`11`、`12`，依赖安装与 Tauri 外部退出码传播，以及完整环境的 validate-only `0`；测试不得触碰真实依赖、Cubism、app-data 或启动 Tauri。

启动文件尚不存在时测试应先失败，再添加最小实现使测试通过。

### 6.2 Windows 边界静态契约

测试递归读取 `src-tauri/src` 下的 Rust 文件，以小型 Rust 非代码文本遮罩排除明显注释和字符串字面量后查找直接 Windows API 标记，并断言命中只位于明确允许清单。每个 Rust 文件只读取一次，实际命中文件必须与 canonical allowlist 精确相等。该测试是对现状的冻结保护，不尝试执行其他系统的编译。

### 6.3 自动验证

实现完成后至少执行：

```powershell
Set-Location apps/desktop
npm test
npm run typecheck
npm run build

Set-Location src-tauri
cargo check
cargo test --lib
cargo fmt -- --check
```

完整 Rust 测试可能需要约两分钟；不得把工具超时直接判定为测试失败。

### 6.4 人工启动验证

自动门禁通过后，双击根目录启动文件，确认：

- 只有一套 Tauri/Vite 开发实例被启动。
- 桌宠窗口正常出现且托盘可用。
- 设置窗口能够打开。
- 控制台能看到 Vite、Cargo 和 Tauri 输出。
- 使用 `Ctrl+C` 或应用退出流程后开发子进程能够结束。
- 不触发生成请求、不删除宠物或草稿。

依赖缺失和 Cubism 缺失分支优先由静态契约与安全的路径替身验证，不破坏当前已准备好的真实开发依赖。

## 7. 第一轮测试衔接

一键启动和自动门禁完成后进入第一轮产品测试。第一轮重点记录：

- 冷启动、托盘、窗口显示与退出。
- 默认 Live2D 和现有用户宠物切换。
- 设置窗口反复打开、关闭后的进程与内存变化。
- 主进程、WebView2 子进程和 GPU 进程的总私有工作集。
- 隐藏与显示后的 CPU、内存和动画恢复。
- 三条创建入口的非付费浏览流程。

测试中发现的每个缺陷先形成可复现步骤和失败测试，再决定最小修复；本轮不预先扩展新功能。

## 8. 完成标准

- 用户能够在 Windows 上从仓库根目录双击启动完整开发应用。
- npm 依赖缺失时自动安装。
- Cubism 缺失时不会静默降级。
- 启动失败可见、可诊断并返回非零退出码。
- Windows 原生代码直接使用范围被静态契约冻结。
- Windows 编译、测试、类型检查和构建门禁通过。
- 未触碰真实 provider、敏感 API Key、正式素材、用户宠物数据和受保护 worktree。
