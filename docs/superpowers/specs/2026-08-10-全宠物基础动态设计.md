# 全宠物基础动态设计

## 目标

所有处于“可使用”状态的宠物都必须具备呼吸和微动。该能力在宠物生成与资源编译过程中形成，不作为用户可选择、可配置或需要额外等待的步骤。

默认猫继续使用 Cubism Live2D；通过图片创建、引导组合或直接认领得到的非 Cubism 宠物使用统一的动态单图运行时。两种技术实现共享相同的宠物动作语义，对用户统一表现为有生命感的桌面宠物。

## 产品原则

- 创建界面不出现“生成动画”“启用呼吸”“渲染器类型”等技术选项或状态。
- 候选预览使用与桌面一致的动态运行时，用户确认的是最终动态效果，而不是静态图。
- 动态资源未准备好时，宠物不能进入 `ready`，也不能以静态图冒充创建完成。
- 呼吸只变形胸腹区域；脸、眼睛和头部不参与局部呼吸变形。
- 微动允许整只宠物围绕身体重心进行极轻的位移和旋转，但不改变面部结构。
- 当前阶段不实现转头、眨眼、嘴巴开合、表情切换或肢体动作。
- 动效算法可以持续升级，并自动改善已创建宠物，无须用户重新生成。

本规格只实现共享动态资源与现有图片创建链路的接入，不新增“引导组合”和“直接认领”的用户界面；这两条后续链路必须复用同一动态资源编译入口，不能产出静态完成态。

## 方案选择

### 方案 A：运行时对所有静态图片直接套用固定动效

实现最快，但生成资源没有动作语义，难以保证胸腹范围正确，也不符合“生成时已经具备能力”的要求。

### 方案 B：生成动作语义，运行时统一执行（采用）

生成阶段根据透明轮廓产出胸腹区域、身体重心、摆动轴和配置版本；运行时根据这些语义执行中央维护的呼吸与微动算法。生成资源具有明确能力，同时算法参数仍可集中升级。

### 方案 C：为每只宠物生成 Cubism 模型

可以承载更复杂的动作，但单张图片不能可靠提供部件分层、遮挡关系和面部状态，不适合作为当前 MVP 的基础条件。

## 资源格式

新增 `schemaVersion: 3`、`renderer: "animated-image-v1"` 的运行时清单。Live2D 继续使用现有 schema v2，旧的静态单图使用 schema v1，并在使用前迁移到 v3。

v3 清单包含：

```json
{
  "schemaVersion": 3,
  "renderer": "animated-image-v1",
  "petId": "pet-user-1",
  "variantId": "variant-1",
  "image": "body.png",
  "motionProfile": "motion-profile.json",
  "files": [
    { "role": "main", "relativePath": "body.png", "sha256": "..." },
    { "role": "motion-profile", "relativePath": "motion-profile.json", "sha256": "..." }
  ]
}
```

`motion-profile.json` 只保存由形象决定的语义数据，不烘焙最终动画帧：

```json
{
  "profileVersion": 1,
  "engineProfile": "life-v1",
  "alphaBounds": { "left": 0.1, "top": 0.05, "right": 0.9, "bottom": 0.96 },
  "breathZone": { "top": 0.46, "bottom": 0.82, "left": 0.22, "right": 0.78 },
  "swayPivot": { "x": 0.5, "y": 0.72 }
}
```

所有坐标均相对于原始图片归一化到 `0..1`。生成器必须保证 `breathZone.top >= alphaBounds.top + (alphaBounds.bottom - alphaBounds.top) * 0.40`，并使变形权重在呼吸区域上下边界归零，以防止变形传入脸部或图片边缘。

`engineProfile: "life-v1"` 的初始中央参数为：呼吸周期 2800 ms、胸腹最大横向缩放为呼吸区域宽度的 2.8%、最大纵向位移为呼吸区域高度的 1.2%；微动周期 5200 ms、最大旋转 0.7°、最大水平位移为画布宽度的 0.45%。这些参数属于运行时版本，可在后续版本统一调整。

## 生成与创建数据流

1. 当前图片创建链路产生规范化的正面或近正面宠物候选图；后续引导组合和直接认领复用相同入口。
2. 背景去除完成后，动作配置生成器读取透明轮廓，计算 `alphaBounds`、`breathZone` 和 `swayPivot`，并原子写入候选目录的 `motion-profile.json`。
3. 候选只有在图片和动作配置都通过校验后才进入可预览状态。
4. 创建页使用动态单图运行时展示候选，不增加用户可见步骤。
5. 用户确认后，资源编译器复制 `body.png` 和动作配置、计算哈希并写入 v3 清单。
6. 资源完整性检查通过后，宠物才进入 `ready` 并允许切换至桌面。

动作配置生成是本地确定性步骤，不依赖 SaaS 服务；生成失败时复用已有任务重试/恢复机制，不把宠物降级为静态完成态。

## 动态单图运行时

新增 `AnimatedImageRenderer`，继续实现现有 `PetRenderer` 接口：

- `load` 加载图片与动作配置并准备透明 Canvas。
- `resize` 保持现有 contain 布局和高 DPI 行为。
- `playMotion("idle")` 启动基础生命循环；暂停、隐藏和销毁沿用现有宿主生命周期。
- `update(deltaMs)` 使用单调累计时间计算呼吸相位与微动相位，不依赖固定帧率。
- 呼吸通过分片或网格变形只重绘胸腹区域；胸腹上方保持原像素几何，不进行局部缩放。
- 微动在最终合成阶段围绕 `swayPivot` 做极小的整体变换，不产生面部局部变形。
- Canvas 尺寸保持稳定，命中区域使用中性轮廓加上最大微动包络，避免每帧重算窗口区域。

运行时种类扩展为 `live2d | animated-image | static-png`。`static-png` 只保留给错误诊断和受控预览回退，不能作为用户宠物的 `ready` 运行时。

## 旧宠物迁移

现有 schema v1 用户宠物在应用启动后的资源恢复阶段执行一次无感迁移。恢复阶段先于活动宠物挂载和设置目录读取，不在只读目录查询中修改文件：

1. 校验原 `body.png` 和 v1 清单哈希。
2. 在临时目录生成并校验动作配置与 v3 清单。
3. 使用原子替换提交新资源；失败则保留原文件，不产生半迁移状态。
4. 迁移成功后立即通过动态单图运行时加载。
5. 迁移失败的宠物标记为不可就绪并给出可恢复错误；不以静态图继续显示为成功。

保留原始上传图、候选图、抠图、身份资料和生成任务数据，供未来表情与动作资产重新生成时使用。

## 兼容未来动作

v3 的动作配置是可版本化能力描述，不承诺面部能力。未来增加表情、眼睛、嘴巴、耳朵、尾巴或肢体动作时，通过新的资源文件、能力字段或新 renderer 版本扩展，不改变当前 `PetRenderer` 上层交互协议。

当前版本不提前创建虚假的面部参数，也不根据单张图片模拟转头。

## 错误处理

- 图片或动作配置缺失、哈希不符、坐标越界、呼吸区域覆盖脸部安全区时，资源判定为 corrupt 或 retryable，不进入 `ready`。
- 热切换候选加载或探测失败时，保留原宠物，不提交活动宠物状态。
- 旧宠迁移失败时保留原始资源和数据库事实，以便重试或删除。
- 内置 Live2D 加载失败仍使用现有恢复机制，但静态回退不被视为新增宠物的合格完成态。

## 测试与验收

### Rust

- 动作配置生成结果位于透明轮廓内，胸腹上边界满足脸部安全约束。
- v3 清单和动作配置严格解析，拒绝越界、遍历、缺文件和哈希错误。
- 编译结果同时包含 `body.png`、`motion-profile.json` 和 v3 清单。
- v1 到 v3 迁移原子、幂等，失败不破坏旧资源。
- 目录与活动宠物服务不把未迁移或动态资源损坏的用户宠物标记为 `ready`。

### TypeScript

- v3 解析器只接受 `animated-image-v1` 和合法动作语义。
- 动态渲染器在不同帧率下产生相同相位结果。
- 呼吸变形不改变胸腹安全线上方的绘制几何。
- 微动不超过中央配置的最大位移和旋转。
- 隐藏、恢复、切换、回滚和销毁不泄漏帧循环或 Canvas。
- 创建候选预览和桌面加载走同一个动态运行时入口。

### 真实桌面验收

- 默认 Live2D 猫行为不回退。
- 新建宠物在候选预览阶段已经呼吸和微动。
- 点击“满意，出现在桌面”后保持同一形象和同一动态节奏。
- 现有用户宠物首次使用后自动获得呼吸和微动。
- 呼吸不带动脸部、眼睛或头部局部变形。
- 切换、删除、重启和全屏隐藏恢复均不破坏动态状态。

## 完成标准

只有当现有图片创建链路产出满足动态清单约束的资源、后续创建链路只能通过同一编译入口接入、现有 v1 用户宠物可以无感迁移、候选预览与桌面均使用动态运行时，并通过自动化与真实桌面验收时，本功能才算完成。
