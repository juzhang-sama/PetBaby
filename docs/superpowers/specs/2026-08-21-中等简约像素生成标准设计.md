# 中等简约像素生成标准设计

状态：待用户书面审阅  
日期：2026-08-21  
适用项目：PetBaby `desktop-pet`

## 1. 决策摘要

PetBaby 的新宠物形象默认从高细节 `pixel-style-v1` 切换为动画优先的中等简约标准：

- 新风格档案 ID：`pixel-style-v2-animation-ready`；
- 继续使用像素生成管线 `route=pixel-v1`，不新建 `pixel-v2` 路由；
- 生成模型继续使用 lk888 的 `gpt-image-2`；
- 逻辑像素网格从 512 调整为 160；
- 主体调色板从默认 32 色调整为最多 24 色；
- 采用大块花纹、清晰轮廓、两级明暗，去掉细碎毛发和次要纹理；
- 保留脸型、耳型、眼色、主要花纹、体型、尾型和标志性特征，仍以“一眼认出来”为第一验收目标；
- 增加稀有身份色保护，防止绿色或金黄色眼睛、小面积标志色被全局量化吞掉；
- 历史 `pixel-style-v1` 任务、审计记录、已安装宠物和哈希继续按原语义读取；
- Live2D 继续冻结，只保留历史资产和兼容代码，不进入本次新生成链路；
- 固定帧动画协议是后续方向，本次先把静态母版变成适合逐帧生成的输入，不在本次迁移中扩展动作数量。

这里的“中等简约”不是把所有宠物画成同一只通用猫，也不是直接照搬 Petdex 的低细节素材。它是在身份还原与动画稳定性之间选择已经过三只宠物实测的中间档。

## 2. 决策依据

2026-08-21 使用三张附件照片，通过项目现有 lk888 `gpt-image-2` 链路生成了三档共 9 张结果：高细节、中等简约、Petdex 式低细节。实验产物位于：

`output/宠物简约风格对比-2026-08-21/`

实验任务 9/9 成功，均为 `1024x1024 RGBA`，半透明比例为 0，最低主体连通占比为 0.998715。三档比较显示：

| 路线 | 身份还原 | 动画制作难度 | 结论 |
|---|---|---|---|
| 高细节 | 最高 | 最高，毛束、细纹和多级阴影容易逐帧漂移 | 不再作为新生成默认值 |
| 中等简约 | 足以辨认三只宠物 | 明显降低，眼、耳、胸、爪、尾区域更干净 | 采用 |
| Petdex 式低细节 | 最低，部分个体差异被压平 | 最低 | 不作为默认值，可保留为未来降级研究 |

Petdex 提供的主要启发是简约角色设计、固定画布、离散状态和预制帧播放。它没有解决“真实照片如何生成同一只宠物”的问题。因此 PetBaby 保留自己的身份分析和用户确认链路，只吸收有助于降低动画生产与运行时复杂度的部分。

## 3. 目标与非目标

### 3.1 目标

1. 所有新创建的照片分身，以及未来复用同一后端的标准宠物和领养宠物 AI 生成入口，默认使用同一套中等简约生成标准。
2. 同一只宠物在静态母版与后续动作帧之间更容易保持脸、花纹、轮廓和颜色稳定。
3. 换成不同用户、品种、毛色和体型后仍复用同一条生成管线，不为单只宠物硬编码画法。
4. 新旧任务都能通过自身记录的风格 ID、提示词版本、风格哈希和后处理参数被准确解释。
5. 桌面端继续消费完整 PNG 或固定帧资源，不需要理解眼睛、胸部或尾巴的身体结构。

### 3.2 非目标

- 不删除、改写或重新量化已经安装的 v1 宠物。
- 不批量重绘当前随应用发布的内置宠物；只有它们未来主动重新生成时才使用 v2。
- 不把历史 v1 审计记录批量转换成 v2。
- 不恢复 Live2D 生成、绑定或运行路线。
- 不在本次迁移中实现 Petdex 的完整 9 行或 11 行动作图集。
- 不引入照片贴脸、部件拼装、语义拆层或实时骨骼形变。
- 不把“最多 24 色”理解为所有宠物必须使用完全相同的固定色板。
- 不将实验脚本直接作为生产实现；实验提示词和量化参数需要进入正式版本化合同。

## 4. 视觉标准

### 4.1 身份优先级

身份特征按以下优先级保留：

1. 脸部轮廓、脸宽、口鼻比例和眼距；
2. 耳朵大小、形状、朝向和耳根位置；
3. 眼睛颜色、眼型和主要表情；
4. 脸部主花纹、额头纹、鼻梁白斑等标志性图形；
5. 主体毛色和胸口、四肢、身体的大块花纹；
6. 身体胖瘦、腿长和整体轮廓；
7. 尾巴长度、粗细、弯曲方式和主要尾纹；
8. 只有不增加逐帧不稳定性时才保留的次要特征。

发生冲突时，身份锚点优先于“更可爱”，清晰轮廓优先于毛发写实，主要花纹优先于细碎纹理。

### 4.2 简化规则

- 使用完整、居中、稳定的标准坐姿，正面到极轻微三分之四视角。
- 头部约占整体高度 38% 至 42%，但不得用统一大头模板覆盖真实脸型和体型差异。
- 全身、四爪、尾根和尾尖必须可见；每边目标透明留白为 6%，机械验收下限为 4%。
- 轮廓使用连续、清晰的深色像素边；不得出现羽化、软笔刷、平滑矢量边缘或发光。
- 毛发改写为少量有方向的大色块，不逐根描绘，不保留随机碎毛和噪点。
- 只使用基础色、暗部色和必要高光，主体采用两级明暗；眼睛等身份区域允许一个额外高光色。
- 小花纹若不是身份锚点则合并到相邻大色块；身份花纹可以简化形状，但不能改变位置、方向或主颜色。
- 眼睛、耳根、胸口、爪子、尾根和尾尖周围必须保持干净，给眨眼、呼吸和摇尾巴逐帧重绘留出稳定区域。
- 输出仍是一张完整宠物 PNG，不输出身体零件或层。

### 4.3 逻辑网格与输出文件

`160x160` 是 v2 的逻辑设计网格，不是桌面端文件尺寸。生产输出继续为 `1024x1024 RGBA PNG`，以兼容现有上传结果、审计、运行资产构建器和 `animated-image-v1` 渲染器。

后处理必须遵循固定顺序：

1. 校验供应商原图为合法 PNG；
2. 去除可识别的边缘棋盘背景并规范为 RGBA；
3. 按 6% 安全留白居中主体；
4. 使用 `BOX` 降采样到 `160x160` 逻辑网格；
5. 对可见主体颜色执行最多 24 色的身份保护量化；
6. alpha 使用多数投票硬化为 0 或 255；
7. 使用 `NEAREST` 映射回 `1024x1024`；
8. 清零完全透明像素的 RGB；
9. 执行 alpha、连通性、留白、色板和后处理审计。

虽然 160 不能整除 1024，但所有静态图和动作帧必须使用同一个确定性坐标映射，因此同一逻辑像素在每一帧中的输出边界保持一致。后续动作生产也必须先在 160 逻辑网格上重绘，再统一导出 1024 文件，禁止直接在 1024 输出图上做任意缩放或插值。

### 4.4 调色板与身份保护色

v2 主体最多使用 24 种可见 RGB 颜色，透明色不计入。量化必须使用以下确定性流程：

- 生产环境锁定同一 Pillow 主次版本，并固定使用 `Image.Quantize.MAXCOVERAGE`；不允许替换量化实现，也禁止继续使用 v1 的全局 `MEDIANCUT`；
- 只统计 alpha 大于 0 的主体像素，透明黑不得占用色板槽位；
- 先将可见主体临时量化为 64 个候选色簇；可见面积占比大于等于 5% 的色簇定义为主色簇；
- 面积占比在 0.05% 至 5% 之间，且与每个主色簇的最小 CIEDE2000 色差大于等于 18 的色簇，定义为身份保护候选；常见对象包括绿色或金黄色眼睛、粉色鼻子、特殊斑点和尾纹；
- 候选按“与最近主色簇的 CIEDE2000 色差乘以面积占比平方根”降序排列，同分时按 RGB 数值升序排列，固定取前 4 个；
- 最多 4 个保护色包含在 24 色总预算内，其余色位由最大覆盖算法分配；
- 量化后每个保护色必须存在一个可见匹配色，CIEDE2000 色差不大于 12；否则本次后处理判为质量失败，不得静默交付失去眼色或标志色的结果；
- 不通过抖动伪造颜色，量化 dither 固定为 `NONE`。

CIEDE2000 的 sRGB 到 Lab 转换、白点和舍入精度必须作为后处理合同的一部分固定，并由测试向量约束，避免 Python 依赖升级后产生不同保护色排序或输出哈希。

机械保护只防止稀有颜色被算法吃掉，不能判断颜色是否属于正确身体部位。因此三只基准宠物仍需要视觉身份回归。

## 5. 提示词合同

v2 新建独立资产包：

`services/appearance-generation/src/photo_avatar_backend/assets/pixel-style-v2-animation-ready/`

至少包含：

- `风格档案.json`；
- `提示词合同.md`；
- `认可参考图.png`；
- 与现有动作工具兼容的 `标准猫体模板.json` 副本。

v2 不直接引用 v1 目录中的模板文件。两个版本可以在创建 v2 时内容相同，但各自的资产包和哈希必须自包含，后续修改 v2 不得改变 v1 的历史解释能力。

不得原地修改 `pixel-style-v1` 目录中的任何权威资产。v2 提示词必须明确：

- 输入照片只提供身份，不复制背景、光线、构图和原姿势；
- 重新绘制为同一只宠物的完整桌面像素角色，不做滤镜、裁剪、拼贴或贴脸；
- 只保留最强身份锚点、主色块、脸部主花纹、体型、耳型、眼色和尾型；
- 毛发使用少量大色簇，轮廓强、两级明暗、20 至 24 种有目的的颜色；
- 采用稳定坐姿，眼睛睁开、嘴巴闭合，眼、耳根、胸口、爪子、尾根和尾尖清楚可见；
- 禁止文字、水印、配饰、地面、场景、道具、阴影、发光、模糊、渐变、软笔刷、写实毛发、额外肢体和裁切。

生成请求继续只传用户照片。和 v1 当前生产行为一致，`认可参考图.png` 用于版本化视觉审阅与哈希留痕，不作为额外图片输入传给模型，以免被模型当成内容参考而覆盖用户宠物身份。

## 6. 版本与兼容策略

### 6.1 路由不升级

`pixel-v1` 表示“照片身份分析 + 完整像素 PNG + animated-image 运行资产”这条技术管线。本次没有改变管线协议，因此继续使用：

```text
route = pixel-v1
profileKind = pixel-v1
renderer = animated-image-v1
```

风格版本由 `styleProfileId` 区分。这样不需要扩大 SQLite 中多个 `CHECK(route IN ...)`，也不会把纯画风升级错误建模成新的业务路线。

### 6.2 新旧风格双读

合同层允许以下风格 ID：

```text
pixel-style-v1
pixel-style-v2-animation-ready
```

规则是：

- 新会话在第一次身份分析前固定写入 `pixel-style-v2-animation-ready`；
- 重新生成和用户修改沿用当前 revision 已固定的风格 ID；
- 从历史记录恢复时，按记录中的风格 ID 加载对应资产包，不读取“当前默认值”猜测；
- v1 记录继续要求 v1 的风格哈希、参考图哈希和提示词版本；
- v2 记录只接受 v2 对应的哈希和后处理参数；
- 未知风格 ID、缺失资产包或哈希不匹配时明确失败，不回退到另一个风格。

`PixelAppearanceProfile` 的数据形状和 15 项身份特征保持 `schemaVersion=1`，只把 `styleProfileId` 从单一字面量改为受控联合类型。这样既保留历史 JSON，又避免为了未变化的数据结构制造 schema v2。

为保证身份分析尚未生成 profile 时也能无歧义恢复，SQLite v13 在 `photo_avatar_runs` 增加非空 `style_profile_id`：历史行迁移为 `pixel-style-v1`，新像素 revision 写入 `pixel-style-v2-animation-ready`，冻结 Live2D 行写入其历史路线标识。该列只记录生成风格，不新增或改变 route。新的 Python step request 显式携带 `styleProfileId`；解析部署前已持久化、缺少该字段的旧请求时，只允许将它解释为 v1，新的请求一律要求显式字段。

### 6.3 审计升级

历史 `PixelAvatarAuditV1` 原样保留。v2 生成新增 `PixelAvatarAuditV2`，除现有供应商、任务、哈希、尺寸、alpha 和时间字段外，必须记录：

```json
{
  "schemaVersion": 2,
  "logicalGridSize": 160,
  "paletteColorLimit": 24,
  "visibleColorCount": 24,
  "quantizeMethod": "maxcoverage",
  "dither": "none",
  "protectedAccentSlots": 4,
  "protectedAccentCount": 2,
  "downsample": "box",
  "upsample": "nearest"
}
```

`visibleColorCount` 记录最终主体实际使用的颜色数，必须在 1 至 24；`protectedAccentCount` 记录本次实际命中的保护色数量，必须在 0 至 4。Rust 在绑定最终 PNG 时独立重算可见颜色数并与 audit 比对，避免只信任后端声明。

Python 和 Rust 必须按 `schemaVersion` 解析 audit v1/v2，而不是把 v2 字段塞进 v1 精确字段合同。TypeScript 不消费审计 JSON，只需与 Python、Rust 一致解析 profile 和 snapshot 中的 v1/v2 `styleProfileId`。审计哈希继续基于最终 1024 PNG；供应商原图哈希与规范化结果哈希分别保留。

## 7. 跨模块改动边界

### 7.1 Python 生成后端

- 将风格加载器从“只会加载 v1”改为按 ID 加载不可变资产包，并定义唯一的新生成默认值。
- 身份分析、补全提示词和 JSON Schema 输出 v2 风格 ID，同时能解析历史 v1 profile。
- 将 512/32/MEDIANCUT 从隐式全局默认改为风格档案驱动的 160/24/MAXCOVERAGE。
- 新增可见像素量化、保护色审计和 `PixelAvatarAuditV2`。
- `app.py` 判断像素身份结果时按像素 profile 类型或受控风格集合判断，不再只比较 `pixel-style-v1`。
- 任务存储在提交远程任务前固化 style ID；恢复时按已存 ID 重建同一生成环境。

### 7.2 Rust 桌面端

- `domain.rs` 接受 v1/v2 两个 style ID，并确保 revision 内不可变。
- `pixel_contract.rs` 保留 v1 常量，新增 v2 哈希、提示词版本和审计 v2 解析；禁止用一组“当前常量”去校验历史 v1。
- `pixel_remote.rs`、manager 和 store 沿用 `route=pixel-v1`，请求中携带已固定的 style ID。
- runtime asset builder 继续输出 `animated-image-v1`，本次不改变 `body.png`、`motion-profile.json` 和 manifest 的基础路径。
- 数据库无需新增 route；新增 v13 `style_profile_id` 列并将历史像素行回填为 v1，保证 profile 产生前后都能按 revision 无歧义恢复。

### 7.3 TypeScript 桌面合同与界面

- `PixelAppearanceProfileV1.styleProfileId` 改为 v1/v2 受控联合类型，解析器保持严格拒绝未知值。
- `PixelPhotoAvatarSnapshot.route` 继续固定为 `pixel-v1`。
- 生成中的用户文案从强调“高细节像素”调整为“保留身份的简约像素形象”或等价表述。
- 不把旧变量名或 DOM ID 中的 `live2d` 清理工作夹带进本次迁移；它们不是用户可见的生成标准，重命名会扩大风险。

### 7.4 文档

- 将 `docs/设计/猫咪A风格视觉规范.md` 的当前生效标准改为 v2，并明确 v1 为历史标准。
- 更新项目交接文档中的当前主线、默认 style ID、逻辑网格和色板算法。
- 旧规格和旧验证记录只增加“已被 v2 取代”的说明，不重写历史结论。
- 保留本次三档实验的任务账本、机械审计和总览图作为选型证据。

## 8. 数据流与失败行为

新任务的数据流为：

```text
用户照片
  -> 15 项身份特征分析（固定 v2 style ID）
  -> v2 动画优先提示词
  -> lk888 / gpt-image-2 原图
  -> 透明背景和 6% 留白规范化
  -> 160 逻辑网格
  -> 24 色 MAXCOVERAGE + 身份保护色
  -> 1024 RGBA PNG
  -> PixelAvatarAuditV2
  -> 用户预览确认
  -> animated-image-v1 运行资产
```

失败策略：

- 供应商输出非法、主体断裂、留白不足或 alpha 不合格：沿用现有质量失败处理；
- 保护色丢失、可见主体超过 24 色或后处理参数与 v2 合同不符：质量失败，可在现有尝试上限内重新生成；
- v2 风格包缺失或哈希不符：配置错误，立即失败，不降级到 v1；
- 恢复 v1 任务时 v1 包缺失或哈希不符：历史恢复失败并报告具体原因，不用 v2 继续旧任务；
- 用户认为“不像”：保留现有重新生成和修改入口，revision 继续使用 v2，不偷偷提高到 v1 高细节；
- 尾巴在参考照片中不可见：身份分析可将尾型标记为 AI 补全，后续动画不得把“摇尾巴”作为强制动作。

## 9. 验收标准

### 9.1 自动化合同与机械验收

1. v1 profile、audit、snapshot 和已保存 fixture 全部继续通过原有解析与哈希校验。
2. 新任务生成的 profile 固定为 `pixel-style-v2-animation-ready`，route 仍为 `pixel-v1`。
3. v2 最终文件为 `1024x1024 RGBA PNG`，透明像素 RGB 为 0，半透明主体比例不超过 2%。
4. 主体四边机械留白均不低于 4%，最大连通主体占可见像素不低于 95%。
5. v2 逻辑网格为 160，主体可见颜色不超过 24，量化方法、重采样方法和保护色参数完整进入 audit v2。
6. 相同输入 PNG 和相同 v2 参数重复后处理，输出 SHA-256 必须完全一致。
7. 未知 style ID 被 Python、Rust、TypeScript 一致拒绝；v1/v2 哈希串用和 v2 audit 缺少后处理字段被实际消费审计的 Python、Rust 一致拒绝。
8. v1 运行中的任务恢复后仍加载 v1；新会话、重新生成和修改任务按既定版本规则运行。

### 9.2 三只宠物视觉回归

使用本次三张附件作为固定回归集：

- 长毛黑白猫：保留宽白色鼻梁、绿色眼睛、黑白大块分布、蓬松胸毛和深色大尾巴；简化毛束但不能变成短毛通用猫。
- 圆脸狸花猫：保留圆脸、金黄色眼睛、额头 M 纹、主要脸纹、结实体型和环纹尾巴；条纹可合并但不能消失或错位成另一种花纹。
- 修长黑猫：保留修长体型、高尖耳、琥珀眼和长尾；暗部仍能读出身体与四肢轮廓，不能量化成无结构的黑色块。

每只宠物都必须同时通过：

- 与照片并排时，用户能一眼判断为同一只宠物；
- 与高细节版相比，主要身份特征没有实质丢失；
- 与 Petdex 式低细节版相比，脸型、体型和主花纹保留更多；
- 眼、耳根、胸口、爪子和尾巴区域没有由细碎纹理造成的明显动画障碍。

### 9.3 动画就绪回归

风格迁移完成前，至少使用三只回归宠物验证现有呼吸、眨眼和摇尾巴生产工具：

- 眨眼不得改变眼色、眼距、脸部主花纹和头部轮廓；
- 呼吸不得改变前爪、尾尖和腹底地面锚点；
- 摇尾巴只在尾巴清晰可见且可标注时启用，不得牵动身体主轮廓；
- 循环首尾帧一致，所有帧沿用同一 160 到 1024 映射和同一 24 色预算；
- 与 v1 同动作样例比较时，v2 的逐帧漂移、补洞和花纹重画量应明显减少。

这里验证的是“v2 母版确实更适合动画”，不是在本次迁移中上线新的动作协议。

## 10. 测试范围

- Python：风格包双版本加载、默认 v2、历史 v1 profile、v2 提示词、确定性 160/24 后处理、透明像素不占色板、MAXCOVERAGE、保护色成功与失败、audit v1/v2 双读、任务恢复。
- Rust：style ID 联合校验、v1/v2 哈希映射、audit v1/v2、pixel-v1 snapshot、runtime asset 构建、历史 fixture 回归。
- TypeScript：profile 和 snapshot 严格解析、未知 style 拒绝、v1/v2 fixture、界面状态和文案；不新增无调用方的 audit 解析器。
- 集成：新会话生成 v2，历史 v1 会话恢复，v2 重新生成和修改，v2 安装后由 `animated-image-v1` 正常显示。
- 手工视觉 QA：三张附件的静态并排图与代表性呼吸、眨眼、摇尾巴循环。

## 11. 实施顺序

1. 先增加 v2 资产包和双版本风格加载，不切默认值。
2. 扩展 Python profile/audit 与确定性后处理，保持 v1 测试绿色。
3. 扩展 Rust、TypeScript 双版本合同和历史 fixture。
4. 打通 v2 集成生成、预览、安装与恢复。
5. 完成三只宠物静态和动作就绪回归。
6. 最后将新会话默认值切到 v2，并更新当前权威文档。

此顺序保证在 v2 全链路通过前，生产默认值仍是可工作的 v1；一旦默认值切换，所有消费者已经具备 v1/v2 双读能力。

## 12. 完成定义

只有同时满足以下条件，才能宣称“整个项目的生成标准已转为中等简约路线”：

- 新会话默认生成并审计为 `pixel-style-v2-animation-ready`；
- Python、Rust、TypeScript 对 v1/v2 合同理解一致；
- 历史 v1 任务、审计和已安装宠物仍可读取；
- 三只附件宠物通过静态身份和动画就绪回归；
- 当前权威视觉规范与交接文档已切换到 v2；
- Live2D 没有重新进入新生成路径；
- 用户在最终对比图和代表性动作循环中确认 v2 质量可接受。
