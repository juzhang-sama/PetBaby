# 宠物管理与创建闭环设计

## 1. 背景与目标

当前桌面端已经能够在正常启动时显示首只内置 Live2D 猫，并具备已经验收的胸部呼吸和整体微动。但宠物管理仍停留在研发状态：内置猫不出现在设置页，当前选择只保存在进程内存中，切换不会可靠地热更新桌面窗口，删除只处理部分数据库记录，创建向导关闭后也不能稳定续接。

本阶段把已有能力收敛成可交付的本地 MVP，完成两个目标：

1. 产品化宠物管理：内置默认猫可见、当前选择可持久化、无需重启即可安全切换、用户宠物可完整删除。
2. 补全 M4 创建闭环：单候选生成可续接、可编译、可立即设为当前宠物，失败后可以恢复或重试。

本设计选择“两阶段热切换”：候选宠物先在桌面宠物窗口中完成加载和首帧验证，成功后才替换当前宠物并持久化选择。任何失败都不得让当前宠物消失。

## 2. 范围

### 2.1 本阶段包含

- 设置页统一展示内置宠物和用户创建的宠物。
- 使用现有 SQLite `state` 表持久化当前宠物 ID。
- 启动时恢复并校验当前宠物，失效时自动回退到内置猫。
- 桌面宠物窗口内的两阶段热切换与失败回滚。
- 用户宠物的确认删除、关联数据删除和资源清理。
- 单候选创建任务的恢复、重试、接受和放弃。
- 与实际单候选产品流程一致的自动测试和 M4 手工验收清单。

### 2.2 本阶段不包含

- SaaS 后端、账号同步、云端宠物库和跨设备同步。
- 多候选生成与四选一界面。
- 宠物重命名、排序、导入导出和云端备份。
- 继续调整 Cubism 模型、呼吸幅度或整体微动参数。
- 头部跟随、转头、眨眼、眼球跟随和嘴巴开合。

## 3. 产品规则

### 3.1 内置默认宠物

- 固定 ID 为 `pet-live2d-v1`，显示名称为“默认猫 · Live2D”。
- 它是随应用发布的虚拟目录项，不写入普通 `pets` 表，避免升级或清库时被误删。
- 它始终排在宠物列表首位，可以设为当前宠物，但不显示删除入口。
- 它既是首次启动默认值，也是用户宠物失效或被删除后的安全回退项。

### 3.2 当前宠物

- SQLite `state` 表中的 `app:active_pet_id` 是跨重启的权威记录。
- `ActivePetSession` 只保存本进程已提交的镜像状态，不能再作为唯一来源。
- 首次启动没有记录时使用并保存 `pet-live2d-v1`。
- 用户选择宠物或接受新宠物后立即切换，不要求重启应用。
- 新宠物加载、首帧验证或持久化任一步失败时，原宠物继续显示，原选择保持不变。

### 3.3 删除

- 内置宠物在 UI 和后端两层都禁止删除。
- 删除用户宠物必须二次确认，并明确说明本机生成结果和资源也会被清理。
- 删除当前用户宠物时，必须先通过同一套热切换流程切回内置猫并持久化，再开始删除。
- 删除非当前宠物不能影响桌面上正在运行的宠物。
- 删除操作应可重试；重复清理已经不存在的文件不得导致数据库状态回滚或应用崩溃。

## 4. 架构与职责

### 4.1 宠物目录服务

后端新增聚合目录能力，将固定的内置宠物描述与 `PetRepository` 中的用户宠物组合成统一的只读目录结果。每个目录项至少包含：

- `petId`、来源类型（`builtin` 或 `user`）、物种和创建时间；
- 是否为当前宠物、是否可删除；
- 生命周期状态：`ready`、`generating`、`generationFailed`、`awaitingConfirm`、`compileRetryable`、`awaitingActivation` 或 `corrupt`；
- 可供设置页显示的简短问题说明。

用户宠物的状态由已有 `pets`、`generation_jobs`、`appearance_variants`、运行时 `variants` 及资源文件共同投影得出，不新增一套只存在于前端内存中的真相源。内置宠物通过固定描述器加入目录，不伪造数据库记录。

### 4.2 当前选择服务

后端收敛当前选择的读取、校验和提交：

- 读取 `app:active_pet_id`，缺失时返回内置猫。
- 对用户宠物校验数据库记录、运行时清单、清单引用文件及完整性信息。
- 对内置宠物使用同一运行时清单契约进行校验。
- 仅在桌面窗口报告候选宠物已可显示后，提交新的持久化 ID，并同步 `ActivePetSession`。
- 持久化失败时不得改变内存会话；提交顺序保持 SQLite 成功后再更新会话镜像。

启动恢复发现用户宠物缺失或损坏时，记录诊断信息，回退并修复持久化 ID 为 `pet-live2d-v1`。若内置猫自身也无法加载，则显示明确的运行时错误状态，不伪装成切换成功。

### 4.3 桌面热切换协调器

真正掌握渲染器的桌面宠物窗口负责热切换，设置窗口只发起请求并显示结果。协调器按 `requestId` 串行处理，忽略已过期结果：

1. 后端解析目标宠物并返回经过校验的运行时资产描述。
2. 桌面窗口创建独立的隐藏候选渲染器，不复用当前渲染器的画布和生命周期。
3. 候选渲染器完成资产加载、模型契约校验和首个非空白帧探测。
4. 候选就绪后暂停并隐藏旧渲染器，显示候选，再请求后端提交当前宠物 ID；创建接受请求同时携带需要接受的候选 ID。
5. 提交成功后销毁旧渲染器，并向设置窗口返回成功结果。
6. 加载或提交失败时销毁候选，恢复旧渲染器的显示与动画，并返回结构化错误。

设置页在请求结束前禁用重复切换。协调器本身仍必须防重入，从而处理双击、窗口重复事件和迟到响应。切换不能通过刷新整个宠物窗口实现，以免透明窗口闪烁或在失败时短暂无宠物。

普通切换只更新 `app:active_pet_id`。创建接受的提交则在同一个 SQLite 事务中更新当前 ID 并把对应候选标记为已接受，事务成功后才更新 `ActivePetSession`，从而不产生“桌面已切换、候选却仍未接受”的半完成状态。

### 4.4 删除服务

删除由后端单一服务编排，不能继续由 `pet_delete` 和 `gen_cleanup_pet` 各自执行不完整清理：

1. 校验目标不是内置 ID，并读取该宠物精确关联的 job ID、variant ID 和资源路径。
2. 若目标是当前宠物，由调用方先完成切回内置猫；后端再次校验当前选择，避免竞态误删。
3. 将该宠物资产目录和其精确关联的 job 目录原子移动到应用数据目录下的隔离回收区，目录名包含操作 ID。
4. 在一个 SQLite 事务中显式删除该宠物的运行时变体、外观变体、生成任务、身份档案和宠物记录，不依赖未确认启用的外键级联。
5. 数据库事务失败时把隔离文件恢复原位并返回错误；事务成功后再永久清理隔离目录。
6. 最终文件清理失败时，宠物在产品层面已删除，但 UI 必须显示“已删除，残留文件稍后重试清理”的警告；应用下次启动继续清理有操作标记的隔离目录。

现有 `gen_cleanup_pet` 会扫描宽泛的 job 目录，必须改为复用删除服务，只处理数据库中明确属于目标宠物的 job，禁止影响其他宠物任务。

若当前宠物已经安全切到内置猫、随后删除事务失败，则目标宠物保留在列表中并允许重试，内置猫继续作为当前宠物；系统不自动切回待删除宠物，避免在删除失败与资源恢复期间再次加载不确定状态。

### 4.5 创建恢复服务

创建流程保持一个生成任务对应一个候选结果。可恢复阶段由持久化记录投影，而不是保存整个前端向导对象：

- 最新任务处于排队、提交或运行状态：恢复轮询，显示“生成中”。
- 最新任务成功且已有可预览外观变体、尚无可用运行时变体：恢复到候选确认或编译重试。
- 已生成运行时变体但尚未成为当前宠物：恢复到“设为当前宠物”。
- 最新任务失败：保留同一个 `petId` 和身份资料，允许重新上传图片并创建新的 job。
- 已完成热切换并持久化：创建流程结束，该宠物作为普通可用宠物展示。

用户只有在提交生成、创建出持久化宠物记录后才具备跨窗口续接能力；尚未提交的表单草稿不在本阶段持久化。

同一宠物只把创建时间最新、且未放弃的 job 作为当前创建任务。用户发起重试后，新 job 取代旧 job 的向导展示；旧记录和产物不再作为候选出现，并在放弃或删除该宠物时一并精确清理。

“接受候选”是一个完整业务动作：编译运行时资产、用热切换协调器预加载并显示、提交当前 ID，最后把候选标记为已接受。编译成功但热切换失败时保留编译产物和候选，状态回到可重试，不显示“已出现在桌面”。“放弃创建”复用完整删除服务。

## 5. 关键数据流

### 5.1 应用启动

1. 后端打开 SQLite 并恢复未完成的生成任务。
2. 当前选择服务读取 `app:active_pet_id`，缺失时补写内置 ID。
3. 校验目标宠物；无效用户宠物回退内置猫并修复记录。
4. 桌面窗口加载校验后的目标宠物。
5. 设置页通过统一目录接口读取与桌面一致的当前状态。

### 5.2 设置页切换

1. 设置页生成唯一 `requestId` 并进入忙碌状态。
2. 桌面窗口执行候选预加载和首帧探测。
3. 候选就绪后完成可回滚的视觉替换和后端持久化提交。
4. 设置页仅根据相同 `requestId` 的最终结果刷新列表或显示错误。

### 5.3 接受新宠物

1. 从成功 job 获取其唯一候选和抠图资源。
2. 编译运行时资产并校验清单。
3. 走与设置页相同的热切换流程。
4. 提交成功后标记候选已接受、刷新目录并结束向导。
5. 任一步失败都停留在可重试阶段，不删除成功生成的候选。

### 5.4 删除当前宠物

1. 用户确认删除。
2. 热切换到内置猫并持久化。
3. 删除服务隔离资源、提交数据库事务、清理隔离目录。
4. 设置页刷新目录；若只有最终文件清理失败，则显示警告但不把已删除宠物重新加入列表。

## 6. 设置页与创建页表现

- 内置猫固定在列表首位，显示“默认猫 · Live2D”和当前标记，不显示删除按钮。
- 用户宠物沿用现有物种与创建时间信息，不在本阶段引入命名系统。
- `ready` 项可设为当前；`generating` 项显示进度和“继续创建”；`generationFailed` 项允许重新上传并沿用原宠物记录；`awaitingConfirm`、`compileRetryable` 项进入候选页；`awaitingActivation` 项可继续“设为当前宠物”；`corrupt` 项不可切换，可删除并显示损坏原因。
- 切换、接受或删除期间，相关按钮显示进行中状态并禁用重复提交。
- 创建页明确显示生成、候选确认、编译、切换四个阶段；候选始终只有一个。
- 所有成功提示以最终提交结果为准。编译完成不能提前提示“宠物已出现在桌面”。
- 可恢复错误显示用户可执行的下一步，例如“重试切换”“重新上传”“删除损坏宠物”；底层诊断保留在日志中。

## 7. 错误模型与并发规则

- 切换结果至少区分：目标不存在、资产损坏、模型加载失败、空白帧、持久化失败、请求过期和桌面窗口不可用。
- 设置页显示简洁中文错误，日志包含 `requestId`、`petId`、阶段和原始错误链。
- 同一时刻只允许一个切换提交；新请求不得破坏正在显示的旧宠物。
- 删除与切换对同一宠物互斥。删除服务提交前必须再次检查当前 ID。
- 生成轮询和窗口重开可以重复执行；恢复、删除和隔离目录清理都必须幂等。
- 任何无法证明成功的操作都不能显示成功文案。

## 8. 测试策略

### 8.1 Rust 自动测试

- 当前 ID 的缺省、读写、用户宠物失效回退和内置 ID 保护。
- 目录聚合及各创建状态的投影。
- 删除计划只包含目标宠物的资源和 job。
- 隔离成功、数据库失败恢复、重复清理以及残留回收区重试。
- 显式事务删除所有关联表，且不影响另一只宠物。

纯逻辑先写失败测试，再实现；文件系统测试使用独立临时目录。

### 8.2 TypeScript 自动测试

- 设置列表将内置猫置顶并正确显示当前、状态和允许操作。
- 热切换协调器成功提交、加载失败保留旧宠物、持久化失败回滚、迟到请求被忽略。
- 创建状态恢复到轮询、候选确认、编译重试或设为当前。
- 接受流程只有在热切换和持久化成功后才进入完成状态。
- 删除当前宠物必须先切回内置猫；删除失败显示错误且不伪造列表状态。

### 8.3 手工验收

- 选择用户宠物后重启应用，仍显示同一宠物。
- 模拟目标资产损坏，切换失败时原宠物持续显示且可以继续操作。
- 删除当前用户宠物后立即显示内置猫，重启仍为内置猫，数据库及精确关联目录无残留。
- 生成中关闭并重开设置页，可以继续看到进度；生成完成后可以继续确认。
- 编译或切换失败后重开设置页，可以从可重试阶段继续。
- 接受成功后无需重启，桌面立即显示新宠物。
- 内置猫始终不可删除。

现有 `docs/验证记录/M4手工验证清单.md` 必须同步为单候选流程，并在真实 Tauri 桌面环境记录结果。自动测试通过不能替代窗口热切换、透明渲染和重启恢复的手工验收。

## 9. 完成标准

- 设置页、桌面窗口和重启后的当前宠物状态一致。
- 任意切换失败都不会出现空白桌面宠物窗口或丢失原宠物。
- 删除不会误删其他宠物的生成任务或文件，残留清理失败可见且可自动重试。
- 创建任务可以跨设置窗口关闭与应用重启续接，并最终直接切换到新宠物。
- M4 验收清单不再包含四候选旧要求，新增的自动测试和手工验收均有真实结果记录。
- 已验收的 Live2D 呼吸与微动表现保持不变。
