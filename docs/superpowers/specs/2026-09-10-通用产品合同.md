# 通用产品合同（照片 → 桌宠）

**本合同解决什么**：把「用户上传任意猫/狗照片 → 生成与内置宠物同等效果的桌宠」拆成
**输入 / 输出 / 行为 / 失败**四项可验收的契约，作为后续工程的唯一判据来源。
没有这份合同，每一处「没做到」都会退化成静默降级，而静默降级无法被验收。

---

## 1. 事实基线（合同必须建立在今天的真实状态上）

### 1.1 输入侧已存在的硬约束（代码里确实有）

| 约束 | 值 | 出处 |
| -- | -- | -- |
| 张数 | 1–8 | `creation/photo_avatar/source.rs:7,48` |
| 格式 | 仅 JPEG / PNG | `source.rs:69-76` |
| 单张大小 | ≤ 10 MiB | `source.rs:8` |
| 归一化后总计 | ≤ 40 MiB | `source.rs:9` |
| 边长 | ∈ [256, 4096] | `source.rs:10-11,86-95` |
| 像素总数 | ≤ 16M | `source.rs:12` |
| 授权版本 | `photo-avatar-third-party-ai-lk888-no-delete-v2` | `creation/photo_avatar/domain.rs:8` |

### 1.2 输入侧的空白（本合同要补的）

- **没有**「输入是否为猫/狗」的硬判定。物种只在**模型输出的 profile** 上校验
  （`contracts.py:177`、`domain.rs:279`），输入侧只校验格式/大小/分辨率。
- **没有**「单只主体」判定，合影会整张送进模型。
- **没有**「正面/全身」判定，只有 prompt 软引导（`pixel_style.py:166`）。
- 后果：模型把鸟或风景幻觉成 `cat`，species 校验会通过，流程一路继续。

### 1.3 产物现状：两条物理隔离的路径

| | 内置宠物 01–05 | 用户上传 |
| -- | -- | -- |
| 位置 | `apps/desktop/public/builtin-pets/<petId>/` | Rust 安装目录 |
| 解析方 | TypeScript `parseFrameSequenceManifest` | Rust `validate_asset_directory` |
| 产物 | schema 7（帧序列） | schema 3（`animated-image-v1` + life-v1 运动档） |
| 校验能力 | — | 已于 2026-09-10 具备 schema 7（`runtime_assets/frame_sequence.rs`） |

### 1.4 隐式行为：未声明的动作会被静默吞掉

`frame-sequence-renderer.ts:238` 的取法是 `semantics[motion] ?? defaultAction`。
产品实际会发出 **9 个动作**（`pet-presentation-controller.ts`），内置宠物的实际覆盖：

| 宠物 | idle | 左右看 | 双击 | 点击 | 拖拽 |
| -- | -- | -- | -- | -- | -- |
| 01 / 02 / 03 | ✓ | · | ✓ | ✓ | · |
| 04 毛砌墙 | ✓ | · | · | ✓ | · |
| 05 建国 | ✓ | · | · | ✓ | ✓ |

`·` = 键不存在 → 静默回落到待机。**没有任何一只内置宠物声明过左右看 / 睡眠 / 唤醒。**
「点了没反应」与「故意不响应」在数据上**无法区分** —— 这是缺合同导致的，不是 bug。

> **2026-09-10（D3）已修**：9 键全部显式声明，无专属动作的指向 `defaultAction`。
> 见 §4.2 与 §7.2。上表的 `·` 现在一律换成显式的 `"<defaultAction>"`。

### 1.5 不可信字段

- `_provenance` 由 POC 脚本写入、**已过期**（04 写着「无 idleSchedule」，实际 manifest 里有）。
  **不得作为契约字段或验收依据。**

## 2. 输入合同

### 2.1 必须接受

1–8 张 JPEG/PNG，单张 ≤10 MiB、总计 ≤40 MiB，边长 [256,4096]、≤16M 像素；
主体为**家猫（Felis catus）或家犬（Canis familiaris）**。

### 2.2 必须拒绝

- 格式 / 大小 / 分辨率越界 → 沿用 §1.1 既有约束。
- **物种无法判定为 cat 或 dog** → 显式拒绝（新增）。
- **无法在任一张照片中分离出单只可辨认主体** → 显式拒绝（新增）。

### 2.3 物种判定要求（新增，最关键的一条）

- 物种必须来自**图像内容**，不允许从用户输入或默认值推断。
- 只有 `cat` / `dog` 才继续；**判定不确定、多只主体、非猫狗 → 显式失败，禁止「猜一个」。**
- 判定结果必须**贯穿到最终产物**。产物侧的载体**不是 manifest**，而是 SQLite `pets.species`
  （见 §6.2 更正）：`profile.species` → `pets.species`。
- 三端（Python / Rust / TS）对物种的接受集合必须一致：`{cat, dog}`。
  （Python 与 Rust 已具备；**TS 侧目前完全没有 species 校验**，需补。）

## 3. 输出合同

输出分两档，**档位与 §6 的交付承诺严格对应**。同一只宠物只安装一套资产，
不允许两档并存（升级是**替换**，不是叠加）。

### 3.1 L1 输出（现役路径，本合同承诺的范围）

产物是 **schema 3** 资产目录（`renderer: animated-image-v1` + life-v1 运动档），
由 `creation/photo_avatar/pixel_avatar_builder.rs` 写出：

| 要求 | 规定 |
| -- | -- |
| `renderer` | `animated-image-v1` |
| 运动档 | life-v1 motion-profile |
| `image` | 单张像素立绘 |
| `species` | **不在 manifest**；载体是 `pets.species`（见 §6.2） |
| 行为表现 | 程序化呼吸 / 摇摆（无逐帧动作） |

### 3.2 L2+ 输出（升级目标，本合同不承诺）

产物是 **schema 7** `frame-sequence-v1` 资产目录，必须能通过 Rust 资产层校验：

| 要求 | 规定 |
| -- | -- |
| `renderer` | `frame-sequence-v1` |
| `anchorPolicy` | `fixed` |
| `species` | `cat` \| `dog`（与 profile 一致） |
| 画幅 | 640 × 640，透明背景（WebP alpha） |
| 帧路径 | `frames/<actionId>/f%04d.webp`，从 `f0000` 连续编号 |
| `baseImage` | `defaultAction` 的首帧 |
| `files` | 必须**逐帧**列出且 `sha256` 正确（校验会实读比对） |
| `defaultAction` | 必须是被声明的动作 |
| `semantics` | 必须显式声明 §4.1 的全部 9 个动作键（见 §4.2） |
| `_provenance` | 非契约字段，可写可不写，不参与验收 |

## 4. 行为合同（核心）

### 4.1 产品动作全集（9 个）

来源 `pet-presentation-controller.ts`：
`idle`、`look-left`、`look-right`、`react-happy`(双击)、`react-curious`(点身体)、
`carried`(拖起)、`landed`(放下)、`sleep`、`wake`。

### 4.2 semantics 必须覆盖全集（强制，已实现）

**`semantics` 必须显式包含全部 9 个键。**
没有专属动作的，**显式映射到 `defaultAction`**（即明示「此处回落待机」）。

- 理由：键缺失与「故意不做」在数据上不可区分，静默回落无法验收。
  显式映射后，「没做」变成一个**看得见的决定**。
- 成本：**纯声明，零帧成本**。给 04 加 `"carried": "idle-combo"` 不需要重生成任何素材。
- 落地：已进两侧校验器（`PRODUCT_MOTIONS`），见 §7.2。

### 4.3 分级

- **A 级（必须保证有专属反馈）**：`idle`（必须 loop）、`react-curious`（点身体必须有反应）。
- **B 级（必须显式声明，允许回落待机）**：其余 7 个动作。

## 5. 失败合同

### 5.1 拒绝 vs 降级

原则（沿用上一轮「两侧同构、不静默分裂」的结论）：
**能力不足必须显式降级且可被观测，禁止静默假冒成功。**

- 身份/物种/素材质量不达标 → **拒绝生成**（显式失败），不做「先装个凑合的」。
- 已生成但动作缺失 → **允许回落**，但必须在 manifest 里显式声明（§4.2）。

### 5.2 失败分类（沿用现有，勿新增）

`InvalidInput`、`Auth`、`Quota`、`ContentPolicy`、`Unsupported`、
`Network`、`Timeout`、`Provider5xx`、`TemporaryUnavailable`、`LocalStorage`
（`domain.rs:43-54`）。可重试集合：`network / timeout / provider5xx / temporaryUnavailable`。

### 5.3 重试与时限（沿用现有，勿改）

- 每步最多 **3 次** attempt（`store.rs:438-440`、`domain.rs:106`）。
- 单步轮询 deadline **300 秒**（`pixel_remote.rs:91`）。
- 后端并发 **2 worker**（`app.py:147`）。

## 6. 分级交付承诺（诚实部分）

| 级别 | 内容 | 今天的状态 |
| -- | -- | -- |
| **L1** | 身份可辨认 + 程序化呼吸/摇摆（schema 3） | **机制可用；真实照片质量未验收**（见下） |
| **L2** | 帧序列待机循环（schema 7，视觉对齐 04/05） | 不能（依赖 AI 视频链路产品化） |
| **L3** | L2 + 偶发动作（yawn / lick） | 不能 |
| **L4** | L3 + 交互动作（grab-release） | 不能 |

**本合同只承诺 L1。** L2–L4 是「能力允许时的升级」，且升级必须是**替换**而非叠加：
同一只宠物只安装一套资产，不允许 schema 3 与 schema 7 同时存在。

### 6.1 关于 L1 的一处重要澄清

`docs/验证记录/照片分身真实20样本验收.md` 记录的「样本 01 失败、19 个暂停」，
以及 `首只真实照片分身验收.md` 的失败结论，**都属于已废弃的 Live2D V5 旧路线**
（`gpt-image-2` + `renderTextureAtlas` + `half-stand-stretch`），
两份文档自己也标注了「已于 2026-08-18 被像素路线取代，仅作历史留痕」。

**而现役的 pixel / schema3 路线，从未做过真实照片验收** ——
现有验收全部基于 `FakePhotoAvatarProvider` 或合成 PNG，
只能证明链路与动态，**不证明真实宠物身份相似度**。

因此「L1 机制可用」成立，但「L1 质量可用」**尚未被任何证据支持**。
把 L1 视为已打通之前，必须先跑一次真实照片验收并取得通过率。

> 说明：04/05 那种质量的内置宠物是**逐只人眼验收 + 反复重生成**出来的
> （见 Seedance 翻车史）。把它自动推广到任意照片，是本研究方向的核心难题，
> 不能在合同里假装已经解决。

### 6.2 更正（2026-09-11）：species 载体是数据库，不是 manifest

**原判断（错误）**：§2.3 要求「`profile.species` → `manifest.species` 两端相等」，
而 schema 3 的 manifest 没有 `species` 字段，因此要求给 schema 3 加一个可选 `species`。
**更正**：这条链路本身就是错的。species 的真实载体是 SQLite 的 `pets` 表，不是资产 manifest。

代码证据：

- `pets/catalog.rs:241` 从 `pets` 表读 `species` → `PetCatalogEntry.species`
  → 经 `pet_catalog_list`（`settings.ts:227`）到 UI。
- schema 3 manifest（`pixel_avatar_builder.rs:174-184`）字段只有
  schemaVersion / renderer / petId / variantId / image / motionProfile / files —— 本来就不该有 species。
- `frame_sequence.rs` / `frame-sequence-manifest.ts` 里的 `species` 是 **schema 7 帧序列**的字段，
  与用户上传的 schema 3 无关。

**真正的缺陷（两个，都不影响外观）**：

1. **`pets.species` 被硬编码**：`pets/repository.rs:359` 调
   `insert_on_connection(db, Species::Cat, mode, method, source_template)` —— 上传宠物**恒记 cat**，
   即使 D2 已允许分析结果判为 `dog`。预留发生在会话开始（分析之前），要修正需在 profile 落地后补一次 UPDATE。
2. **`species` 当前没有任何消费者**：`PetCatalogEntry.species` 在 Rust 侧被填充、
   在 TS 侧被声明（`pet-catalog-contract.ts:18`），但**全仓库非测试代码没有一处读取它**
   （`species` 只出现在契约声明、校验器与测试里）。UI 不显示物种，运行时也不按物种分支。

**结论（2026-09-11 决策）**：
- **不给 schema 3 manifest 加 `species` 字段** —— 那会凭空造出第二个同义的真源，且无消费者，属典型过度设计。
- **硬编码 `Species::Cat` 也暂不修** —— 修它需要把物种从分析步骤回写到已预留的 pet 行，
  在拿到消费者之前属于投机性改动。
- 触发条件：**当第一次有代码真的按物种分支时**（例如按物种选帧序列资产、UI 显示「猫/狗」），
  同时做这两件事。届时以 `pets.species` 为唯一真源。

> 教训（沿用 §1.5 的规矩）：**引用字段前先确认它是谁的载体、有没有人读**。
> 「某个字段不在文件里」不等于「信息到不了产物」—— 信息可能走数据库。

## 7. 已确认的决策（2026-09-10 老王定版）

| # | 决策 | 结论 | 落地状态 |
| -- | -- | -- | -- |
| D1 | 本合同承诺到哪一级 | **只承诺 L1**，L2–L4 列为能力项 | 已写入 §6 |
| D2 | 是否引入输入侧「非猫狗 / 多只」硬拒绝 | **引入** | **已实现**，见 §7.1 |
| D3 | `semantics` 是否强制覆盖 9 键 | **强制** | **已实现**，见 §7.2 |

### 7.1 D2 已实现（输入侧硬拒绝）

根因：分析步的 JSON schema 把 `species` 限死成 `["cat", "dog"]`，
模型在**结构上无法表达「这不是猫/狗」**，只能二选一 —— 鸟、风景、多只合影都会被硬塞进某个物种。

改动（`services/appearance-generation/src/photo_avatar_backend/`）：

- `pixel_prompt.py` 新增 `ANALYSIS_UNSUPPORTED_SPECIES = "unsupported"`；
  分析步 schema 的 `species` enum 变为 `["cat", "dog", "unsupported"]`，
  **补全步仍然锁死到已判定物种**（`[species]`）。
- `analysis_prompt` 明确要求：照片必须包含**单只**明确可辨认的猫或狗；
  否则 `species` 返回 `"unsupported"` 且 traits 留空，**禁止为了满足 schema 而猜物种**。
- `pixel_avatar.analyze_pixel_identity` 在**提交补全步骤之前**检测该值并抛 `ContractError`
  → 映射为 `invalidInput`（用户可见「生成请求无效，请检查照片后重试。」）。
  提前失败同时省掉一次付费调用。

**已知局限（必须在验收时承认）**：这条硬拒绝**依赖模型诚实**。
若模型把鸟幻觉成 `cat`，判定依然会通过。它把「结构性强迫二选一」变成了「模型可以选择拒绝」，
显著降低但不消除误判率。真正的兜底需要人工确认或第二道独立判定。

### 7.2 D3 已实现（semantics 强制覆盖 9 键）

规则：`semantics` 必须显式声明 §4.1 的全部 9 个动作键；没有专属动作的**显式指向
`defaultAction`**。校验器（两侧同构、错误文案逐字一致）：

```
semantics must declare every product motion: missing look-left, look-right, ...
```

9 键常量以 `PRODUCT_MOTIONS` 为名落在两处，唯一真源是
`pet-presentation-controller.ts` 的 `dispatch`（改动时必须同步）：

- `apps/desktop/src-tauri/src/runtime_assets/frame_sequence.rs`
- `apps/desktop/src/runtime/frame-sequence-manifest.ts`

**实际影响面（比 §7.2 原估计大，已全部改完）**：

| 类别 | 文件 |
| -- | -- |
| 两个校验器 | `frame_sequence.rs`、`frame-sequence-manifest.ts` |
| 校验器夹具 | Rust `minimal_manifest`、TS `validV6Manifest`、Rust `loader.rs` 的 schema-7 夹具 |
| 用例清理 | `frame-sequence-manifest.test.ts` 中 4 处单键覆盖已删除 |
| 内置资产 | 01 / 02 / 03 / 04 / 05 五个 manifest 补齐 9 键 |
| **POC 生成脚本** | `scripts/poc_合并动作.py`、`scripts/poc_组合循环打包.py` |
| **已产出的真实 manifest** | `output/.../07-合并-呼吸眨眼/`、`output/.../09-组合循环/10-运行时包/` |

最后两项是原估计**遗漏**的：两个 TS 用例会真实解析 `output/` 下的 manifest，
而这两个文件出自 POC 脚本。已同时改脚本（保证以后产出自带 9 键）与补既有文件。

**一处必须承认的取舍**：本规则做成**硬校验失败**（而不是只做 lint），
即「声明不全 → 整只宠物拒绝加载」。这比 §5.1 的「显式降级」更重：
一个缺 `sleep` 声明的资产其实是**可用**的（运行时本来就会回落）。
选择硬失败的理由是让规则无法被绕过；代价是引入了「声明不全 = 资产不可用」。
若日后要放宽，正确做法是降级为 `auditSemanticsCoverage` 报告 + 测试守卫，
而不是在解析器里悄悄容忍。

副作用：`output/` 未被 git 跟踪（`.gitignore:17`），但有两个 TS 用例依赖它，
因此**新克隆的仓库跑不出这两个用例的结果**。这是既有脆弱点，非本次引入。

## 8. 明确不在本合同内

- 内置宠物 01/02/03 的重做（老王已拍板先放着）。
- 记忆缓存 / 内存优化（上一轮结论：不是通用性的第一根因）。
- 具体生成算法（AI 视频模型选型、抠像参数、提示词）——属于实现，不属于合同。
