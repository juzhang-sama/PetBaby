## 1. 背景与问题

照片分身链路已经能够通过 lk888 聚合平台调用 GPT-image-2.0，生成一张包含宠物身份外观的 2048×2048 纹理图。真实任务 `106786157` 的结果证明，模型能够把脸、耳、身体、眼睛和尾巴的 RGB 外观大体放入正确 UV 岛，但不能可靠维护 Live2D 模块要求的 alpha 拓扑。

失败审计对象固定如下：

- 本地 job：`63847454926843658af5209f637863f7`
- session：`session-39e4-18cc41097f1aea24-1`
- revision：`13`
- provider task：`106786157`
- 原始 artifact：`services/appearance-generation/output/task-11-runtime/artifacts/a3eb6a61778c48cd85136aa4e5f67f83.png`
- artifact SHA-256：`5503e493829423f316a348c9c96a54681383d0efb7a76417c9fa2ac0c653e9a0`

对该 artifact 与 `body-balanced-v1` 权威模块纹理逐像素复算得到：

- 总像素：`4,194,304`
- alpha 不一致像素：`3,390,353`，占 `80.832314%`
- 模块外 provider alpha `>=128` 的明显泄漏像素：`1,321,297`
- 模块内 provider 全透明缺失像素：`54,911`
- 以上 `54,911` 个缺失像素的 RGB 全部为 `0,0,0`

因此，简单把模块 alpha 覆盖到 revision 13 上会把这些透明黑色 RGB 暴露为黑洞。revision 13 不能原地修补、不能改写为成功、不能安装，也不能作为新实现的 canonical 输出。

根因不是“模型不会生成宠物”，而是把两个责任错误地同时交给了概率模型：

1. 宠物身份外观的 RGB 生成。
2. Live2D UV 岛、孔洞、断开区域和半透明边缘的精确 alpha 合同。

本设计把这两个责任分离。模型只负责第一项；第二项由受控后端确定性完成。

## 2. 设计目标

### 2.1 必须达到

1. GPT-image-2.0 只决定宠物脸型、毛色、花纹、眼睛和显著特征等 RGB 身份外观。
2. body module 是 alpha、UV 拓扑、动作蒙版和边缘透明度的唯一权威来源。
3. provider 输出不得直接成为可安装纹理，必须经过后端验证、确定性合成和 Rust 独立复验。
4. 任一失败都关闭当前尝试，不得降级为标准猫、静态 PNG、旧 v3 包或伪装成功。
5. 每次尝试可从哈希和版本字段追溯 provider 原始产物、模块合同、工作画布、合成器和 canonical 产物。
6. 核心合成器可复用于不同轮廓、断开 UV 岛、内部孔洞和半透明边缘，不与当前三只模块的偶然相同 alpha 绑定。
7. 真实调用前必须通过离线合同、集成测试、独立复审和动态预览门。

### 2.2 本设计不处理

- 不重新设计身份分析、外观补全、照片同意或三次重试的总体状态机。
- 不修改 Live2D 绑定、动作幅度或 body module 美术源文件。
- 不解决服务器域名、部署证书和生产运维。
- 不实现边缘藏身、领养猫或声音功能。
- 不把自动覆盖检查描述成身份相似度或最终视觉正确性的替代品。

## 3. 方案选择

### 3.1 方案 A：继续要求 provider 原样保留 alpha

优点是代码改动最小。缺点是 revision 13 已证明 GPT-image-2.0 不会稳定遵守逐像素 alpha 合同；提示词更严格也不能把概率行为变成确定性保证。

结论：拒绝。

### 3.2 方案 B：收到 provider PNG 后直接覆盖模块 alpha

优点是表面上能恢复轮廓。缺点是 provider 透明像素的 RGB 可能已经被归零。revision 13 中模块内的 `54,911` 个缺失像素全部为透明黑，覆盖 alpha 后会形成黑洞。

结论：拒绝，且禁止用于修复 revision 13。

### 3.3 方案 C：全不透明工作画布加确定性 alpha 合成

后端向 provider 提供全不透明 UV 工作画布，要求其返回完整 RGB；后端不采信 provider alpha，而是验证 RGB 覆盖后，逐像素应用模块权威 alpha，编码 canonical PNG。Rust builder 再从模块源独立复验 canonical alpha。

结论：采用。该方案将概率模型限制在其擅长的外观生成范围内，把结构正确性收回到可测试、可复算的代码路径。

## 4. 权威数据与术语

### 4.1 权威模块快照

每次 `renderTextureAtlas` 必须在发起 provider 请求前固定以下快照：

- `bodyModuleId`
- `moduleContractSha256`
- `sourceTextureSha256`
- `sourceAlphaSha256`
- `workCanvasSha256`
- `regionMapSha256`
- 工作画布生成器版本
- canonical 合成器版本

同一次尝试从请求、provider 返回、合成到 builder 安装必须使用同一快照。中途模块文件变化属于本地合同错误，立即失败且不消耗新的 provider 调用。

### 4.2 工作画布

工作画布是 2048×2048、全像素不透明的身份中性 PNG，不含标准猫脸、眼睛、毛色、花纹或鼻口身份。它用稳定、非自然的保留色和区域编号表达 UV 岛位置，让 provider 在固定位置绘制 RGB。

工作画布不携带最终 alpha 权威。即使它源自模块纹理的几何信息，交给 provider 的每个像素 alpha 也必须为 `255`。

### 4.3 区域图

区域图是后端专用的无损标签栅格，不发送给用户，也不由 provider 改写。每个要求生成的 UV 区域拥有稳定 ID；背景、断开岛、孔洞和半透明边缘可被单独统计。

区域图与工作画布由同一生成器和同一模块快照产生。两者任一哈希不匹配都禁止调用 provider。

### 4.4 Provider 原始产物

Provider 原始产物是 lk888/GPT-image-2.0 返回的 PNG 字节。它只作为 RGB 候选和审计来源，不是 runtime asset，也不能被 builder 直接安装。

### 4.5 Canonical 纹理

Canonical 纹理是受控后端唯一允许交给 Rust builder 的 PNG。它必须是 2048×2048 RGBA8、straight alpha，并由固定版本的编码器参数确定性输出。

## 5. 组件边界

### 5.1 `UvWorkCanvasGenerator`

职责：

- 读取并验证 body module 合同、neutral texture 和哈希。
- 生成全不透明工作画布及区域图。
- 生成 `sourceAlphaSha256`、画布哈希、区域图哈希和生成器版本。
- 拒绝越界路径、尺寸错误、非 RGBA 模块纹理和同步变更后的伪造索引。

它不调用 provider，不生成宠物身份，也不写 revision 状态。

### 5.2 `ProviderRgbValidator`

职责：

- 解码 provider PNG，验证 2048×2048、像素完整、大小上限和合法色彩模式。
- RGB PNG 按 alpha `255` 解释；RGBA PNG 要求全部像素 alpha 为 `255`。
- 按区域图计算工作画布保留像素、有效 RGB 覆盖和区域变更比例。
- 输出结构化覆盖报告，失败时保留原因和哈希，不产出 canonical PNG。

Provider alpha 可以被记录为诊断数据，但绝不参与 canonical alpha 计算。

### 5.3 `CanonicalTextureComposer`

输入：

- 已通过验证的 2048×2048 provider RGB 栅格。
- 同一快照中的模块 alpha 栅格。
- 模块合同哈希、工作画布哈希、区域图哈希和覆盖报告。

对每个像素 `p` 执行固定公式：

```text
canonical.a[p] = module.a[p]
canonical.rgb[p] = provider.rgb[p]  当 module.a[p] > 0
canonical.rgb[p] = (0, 0, 0)        当 module.a[p] = 0
```

该公式保留模块的半透明抗锯齿边缘，消除完全透明区域的潜藏 RGB，并确保相同输入字节和相同合成器版本得到相同 canonical 字节。

合成后必须立即复算：

- canonical alpha 每个像素与模块 alpha 相等。
- canonical alpha SHA-256 等于快照中的 `sourceAlphaSha256`。
- 完全透明像素的 RGB 全为零。
- canonical PNG SHA-256 与审计记录一致。

### 5.4 Python pipeline 适配器

`renderTextureAtlas` 保留现有请求、轮询和三次尝试边界，但内部顺序调整为：

1. 固定模块快照。
2. 生成并验证工作画布与区域图。
3. 以 `[工作画布, 用户照片 1..8]` 调用 lk888。
4. 下载并保存 provider 原始哈希。
5. 验证 RGB 和区域覆盖。
6. 确定性合成 canonical PNG。
7. 写入 immutable attempt 审计数据。
8. 只把 canonical PNG 和 canonical hash 返回桌面端。

### 5.5 Rust builder 独立复验

Rust 不信任 Python 的“已验证”结论。构建预览、重新打开历史预览、展示和安装前都必须：

- 从 manifest 绑定的 `bodyModuleId` 重新读取模块合同。
- 验证模块合同和 neutral texture 自身哈希。
- 解码 canonical texture 与模块 neutral texture。
- 逐像素比较 alpha，不能只比较尺寸、文件 hash 或可见边界框。
- 验证 manifest 中的 canonical hash。

任何不一致都拒绝预览或安装，并保持旧的已安装宠物不变。

### 5.6 Live2D 动态预览与人工门

自动检查只证明纹理结构可加载，不证明宠物像本人。最终接受前仍需用真实 `Live2DRenderer` 检查中性姿态、八动作峰值与回退、至少两种动作打断，并检查脸、眼睑、耳根、胸腹、尾根、孔洞、白线和纹理错岛。

## 6. Provider 输入输出合同

### 6.1 输入顺序

第一张必须是全不透明工作画布，随后是当次授权的 1 至 8 张宠物照片。顺序进入审计记录，不能由客户端或 provider 适配器重排。

### 6.2 输出要求

Provider 返回必须满足：

- 单张 PNG。
- 精确 2048×2048。
- RGB 或全不透明 RGBA。
- 每个必需区域相对于工作画布的变更像素比例至少为 `95%`。
- 任一区域不存在整块保留色、全黑缺失块或空白区域。
- 不等同于任一标准猫 neutral texture。

`95%` 是技术覆盖门，不是视觉相似度分数。该阈值必须在真实 20 样本调用前由离线 fixture 固定，真实调用过程中不得为提高通过率而修改。

### 6.3 失败分类

以下错误归入当前 `renderTextureAtlas` 尝试失败：

- provider 超时、网络错误或临时不可用。
- 结果不是 PNG、尺寸不符、超限或无法解码。
- RGBA 结果含非 `255` alpha。
- 任一必需区域覆盖不足。
- 结果等同标准猫 neutral texture。
- canonical 合成或复验失败。

模块合同、画布、区域图或本地哈希不一致属于本地非重试错误，应先修复本地状态，不应继续花费 provider 调用。Provider 结果无效属于可重试的生成失败，并计入该 revision 的最多三次尝试。

## 7. 审计与生命周期

每个 attempt 至少记录：

- `sessionId`、`revision`、`attempt`、`providerTaskId`
- lk888 endpoint 配置版本与模型名 `GPT-image-2.0`
- `moduleContractSha256`、`sourceTextureSha256`、`sourceAlphaSha256`
- `workCanvasSha256`、`regionMapSha256`
- `providerRawSha256`、`canonicalSha256`
- 工作画布生成器版本、合成器版本、PNG 编码器版本
- 覆盖报告、失败阶段、错误码与时间戳

API 合同版本和隐私政策版本不删除。它们不进入纹理，但作为调用发生时的审计元数据保留，便于证明当时使用了什么合同和删除政策。

原始照片与 provider 原始产物遵循既有临时数据生命周期。用户接受、放弃、取消或 session 终止后立即清理本地原始素材；provider 支持删除时在生成终态后立即请求删除，不采用“默认保存一周”。若删除失败，记录 `cleanupPending` 并重试，不能把本地成功误写成远端删除成功。

revision 13 的既有 artifact 是本规则生效前形成、且经用户明确同意保留的非人类测试失败 fixture，作为一次性例外继续保留。该例外不能扩展到后续真实 attempt；后续 raw 文件删除后只保留不可逆 hash、覆盖报告和错误审计。

Canonical 角色包、非可逆哈希、覆盖报告和必要审计记录可随已接受角色保留。审计记录不得包含原图 base64、完整提示词中的图片数据或 API key。

## 8. Revision 不可变规则

1. revision 13 永久保持当前失败事实和原始 hash，不改文件、不改 job 为 canonical 成功。
2. 新实现通过离线门后，必须创建新 revision，再进行真实生成。
3. 同一 revision 内最多三次 provider 尝试，每次 attempt 记录不可覆盖。
4. 只有 canonical 合成、Rust 复验和动态预览全部通过，revision 才能进入可接受状态。
5. 失败 revision 不可安装；重新生成不得删除其审计摘要。

## 9. 复用边界

当前 `body-slender-v1`、`body-balanced-v1`、`body-rounded-v1` 的 `guideSha256` 都是 `5d897376...aeef`，`sourceAlphaSha256` 都是 `3911e30b...246`。三者仅模块合同 hash 不同。

因此，在这三个模块上通过测试只能证明“同一 UV/alpha 拓扑绑定到不同模块合同”可工作，不能证明合成器已经支持跨拓扑复用。

核心合成器必须只依赖显式输入的 RGB 栅格、alpha 栅格和区域图，不读取猫专用路径，不内置三个 module ID，也不假设 UV 岛数量。离线测试至少包含以下独立 fixture：

1. 单个连续不透明轮廓。
2. 多个互不接触的 UV 岛。
3. 带内部透明孔洞的轮廓。
4. 含 `1..254` 半透明抗锯齿边缘的轮廓。
5. 岛接近画布边界但不越界的轮廓。
6. 两个 alpha 拓扑不同、RGB 输入相同的对照组。

每个 fixture 都必须逐像素断言 canonical alpha、透明 RGB 归零和确定性 hash。没有这些 fixture，不得宣称合成器可复用到未来新体型或其他宠物物种。

## 10. 测试与验收

### 10.1 离线单元测试

- 工作画布确实全不透明且不含标准猫身份 RGB。
- 模块、画布、区域图和索引任一同步篡改都会失败。
- Provider RGB/RGBA 合法模式、尺寸、大小和全不透明规则有正反测试。
- 六类拓扑 fixture 的输出逐像素满足合成公式。
- 重复运行相同输入得到完全相同的 canonical SHA-256。
- revision 13 作为回归 fixture 时必须被旧 provider-alpha 路径拒绝；禁止生成伪 canonical 成功。

### 10.2 Python 集成测试

- Fake client 收到的第一输入是全不透明工作画布，后续照片顺序不变。
- 覆盖不足、透明 RGB、错误区域、标准猫复制和 provider 失败均关闭。
- 成功响应同时包含 provider raw hash、canonical hash、模块合同 hash、合成器版本和覆盖报告。
- 状态恢复不会把旧 provider raw artifact 绕过合成器交给桌面端。

### 10.3 Rust 集成测试

- 构建、历史预览复开、展示和安装四条路径都逐像素复验 alpha。
- 即使攻击者同步改写 texture 和 manifest hash，只要 alpha 不匹配模块仍然拒绝。
- 新 revision 通过时不复用旧 revision renderer；同 revision 的重叠 poll 只挂载一个 renderer。
- 失败预览不销毁当前已安装宠物，也不产生第二只桌面宠物。

### 10.4 真实 20 样本门

真实调用使用用户已授权的 `01-photos` 中 8 张非人类宠物照片。调用前先冻结样本矩阵、代码提交、配置、模型名、工作画布和阈值；测试中途不挑样、不换阈值、不删除失败项。

“样本”指一个预先登记的 `renderTextureAtlas` revision，可在同一 revision 内最多尝试三次。成功率按 20 个样本计算，不按请求次数稀释：

- 首次技术成功至少 `17/20`，即 `85%`。
- 三次内技术成功至少 `19/20`，即 `95%`。
- 技术成功要求 provider RGB、覆盖、canonical 合成、Rust builder 和真实 Live2D 加载全部通过。
- 所有最终接受并安装的样本，人工视觉检查必须 `100%` 通过。
- 任一未通过人工视觉检查的样本都不得接受或安装，即使技术检查通过。

真实样本证据至少包括每次 attempt 的 task ID、耗时、错误分类、各项 hash、覆盖报告、canonical 图、动态关键帧和人工结论。测试阶段调用次数不设费用上限，但仍执行三次尝试上限，防止用无限重试掩盖低成功率。

## 11. 失败推演

| 场景 | 可观察结果 | 系统行为 | 恢复方式 |
| --- | --- | --- | --- |
| Provider 再次输出透明背景 | RGBA 中出现 alpha 非 255 | 当前 attempt 失败，不合成 | 计入三次尝试，使用同一冻结合同重试 |
| Provider 在局部保留工作画布 | 区域变更比例低于 95% | 当前 attempt 失败 | 重试；三次失败则 revision 失败 |
| Provider 把脸画到错误 UV 岛 | 自动覆盖可能通过，动态预览错位 | 人工视觉门拒绝 | 新 revision 重新生成，不能安装 |
| 模块在调用中被改写 | 合同或源 alpha hash 变化 | 本地非重试失败 | 恢复一致模块后新建 attempt |
| canonical 文件和 manifest 同时被篡改 | Rust 与模块逐像素 alpha 不符 | 预览、展示和安装均拒绝 | 从受信 attempt 重新构建 |
| 进程在 provider 成功后崩溃 | 有 raw hash，无 canonical 成功记录 | 恢复时重新验证并合成，不能直通 raw | 使用同一 immutable attempt 恢复 |
| 合成后预览出现黑洞 | 违反全不透明输入或覆盖合同 | 视觉门拒绝并标记实现缺陷 | 修复合成/验证代码后新 revision |
| 远端删除失败 | `cleanupPending=true` | 本地流程可结束，但审计不得写删除成功 | 后台有限重试并保留错误响应 |
| 同时收到旧、新 revision poll | 旧 renderer Promise 迟到 | 只保留 `sessionId:revision` 当前挂载 | 销毁迟到 handle，不触碰当前 handle |
