# 动作精修流程（标准化）

> 2026-09-20 定。对象：写实风新宠的 one-shot / 交互动作（`yawn` / `lick` / `grab-release`）。
>
> **为什么要这份文档**：内置 04/05/06 的动作支是**人工精修过的** ——
> yawn/lick 只有 119~121 帧、grab-release 只有 81 帧且带 `holdRange: [30, 59]`；
> 而新产线产出的是**整支 12 秒原封不动**（287 帧、无 `holdRange`）。
> 后果就是 pet-7228 的拎起完全不可用（拖拽时整支循环、松手从第 0 帧重播）。
> 本文把「建国身上那道人工工序」变成**固定流水线**，不再依赖某个人的手感。

---

## 一、精修 = 3 个决定

| # | 决定 | 落点 | 谁做 | 现状 |
|---|---|---|---|---|
| 1 | 留哪一段（`frameRange`） | 动作配置 / 打包层 | 机器出候选，人定稿 | ❌ **还没有这个能力** |
| 2 | 保持窗口（`holdRange`） | `actions/<id>.json` | **只能人定稿** | ✅ 键已有，服务只读不猜 |
| 3 | 这支素材要不要重出 | ——（人的决定） | 人看联络表 + 指标 | 靠肉眼 |

**三个决定的共同点：都发生在「视频已生成、还没打包」之间 ⇒ 重打包是 0 算力 ⇒ 可以反复调，不花钱。**

这是整条流程能成立的经济基础：**花钱的只有「生成」，之后想怎么改就怎么改。**

## 二、流水线

### ① 生成视频 —— 花钱，每支一次

- 入口：`generateMotionSource`（服务侧）或 `output/真跑验收-重出grab-release-7228.py --confirm`（单支重出探针）。
- 已有 mp4 一律复用（`_action_videos` 扫 scratch 的 `actions/`）⇒ 只补缺的那支。
- ⚠️ **产线锁死 `VIDEO_DURATION = "12"`**（`frame_pipeline.py`），
  而动作脚本原本只写「约 5 秒」⇒ 模型被迫自己填满多出来的 7 秒 ⇒ **加戏**。
  **所以动作脚本的时间轴必须按 12 秒写**（见下面「四、已验证记录」）。

### ② 量 —— 0 算力，自动

```bash
<python> output/精修-量动作区间.py <动作.mp4>
```

产出（全部是**事实**，不是结论）：

- 逐帧 bbox 曲线（`y0/y1/x0/x1`）与头顶余量统计；
- 首末帧与首帧的差（判「有没有收回去」）；
- **稳定段候选**：相邻帧 bbox 每个边都 ≤4px 的连续段（默认 ≥60 帧），
  按长度排序给前 5 段，并给出最长那段的 `holdRange` 建议值。

判据说明：

- 绿幕判据用 `g - max(r, b) < 40`（**不能**写死 `(0,255,0)` —— 480p 实测是 `(3,178,4)`）；
  传**抠像后的 `frames` 目录**时改用 alpha 阈值（那才是运行时会画的像素）。
- 🔴 **「稳定」的判据是「窗口内极差」，不是「相邻帧变化」**。2026-09-20 实测教训：
  先用相邻帧判据跑出一段 `f84~f203`（120 帧，看着很长），但它是**缓慢漂移** ——
  每步只变 1~2px、首尾却差 45px ⇒ 播放器从 `f203` 硬切回 `f84` 时会**跳变**。
  换成极差判据（窗口内**任意两帧**的 bbox 每边都 ≤ 阈值）后，同一支素材给出
  `f104~f169`（66 帧 ≈ 2.8 秒，接缝差 7px）—— 这才是真能循环的窗口。
  （对照：内置建国的 `[30, 59]` 是 30 帧 ≈ 1.26 秒，新窗口比它还宽裕一倍。）
- ⚠️ **别信服务侧那个「最窄段」候选**：`frames/hold_range.py` 的自动候选是
  「宽度 ≤ 最窄×1.15 的最长连续段」，2026-09-20 实测它挑的是**尾部「收回后的端坐」**
  （确实最窄、也稳定，但语义是「没被拎起」）⇒ 拿它当 `holdRange`，拖拽时循环的是端坐姿态。
  **稳定 ≠ 该拿来循环，语义必须人眼在联络表上确认**（`--sheet` 出图）。

### ③ 定 —— 0 算力，人工

看 `output/真跑验收/<动作>-*.png`（联络表，`output/预览-新grab-release.py` 生成），
在**动作配置**里写两个数：

```jsonc
// assets/motion-prompts/actions/grab-release.json
{
  "holdRange": [86, 205]   // 仅交互动作需要；帧下标闭区间，对着**打包后的帧序列**数
}
```

- `holdRange`：**必须由人填**（理由见「三、关键契约」）。没有它 = 拎起不可用。
- `frameRange`：**当前尚未实现**（本轮决定先不裁区间）。

⚠️ **帧下标要对「打包后的真实帧序列」数**：mp4 抽帧（24fps 得 289 帧）与打包链路
（287 帧）会差 1~2 帧。**先打包一次拿到真实帧序列，再量、再填、再打包** ——
两次打包都是 0 算力，别为了省一次把下标填错。

### ④ 打包 —— 0 算力，自动，可反复

```bash
<python> output/打包-7228.py <attempt>      # attempt 只能是 1..3
```

- `attempt` 是幂等键的一部分（`(sessionId, revision, step, attempt)`）。
- 🔴 **`attempt` 上限 = 3**（`contracts._require_int(payload, "attempt", ..., maximum=3)`），
  第 4 次会直接被 `ContractError: attempt is outside the allowed range` 拒掉。
- **同一个 attempt 想重跑**：把已有目录**改名留档**（`attempt-3` → `attempt-3-无holdRange`），
  再跑同一个号。`build_frame_sequence` 要求**输出目录为空** —— 目录非空会抛 `ValueError`，
  被 `_safe_error` 兜底成 `temporaryUnavailable / provider failed`（**看着像网络问题，其实不是**）。
- **⏱ 一次打包约 8 分钟**（四支动作各自抽帧 + 抠像 + 四项验收 + 打 webp + zip）；
  改一个 `holdRange` 就要重跑一遍，所以**下标先量准再填**，别靠试。
- 验收结论带动作前缀（`grab-release:1-尾巴完整`）；`overall_passed` 要 idle 与每支都过。
- ⚠️ `overall_passed=False` 时脚本 exit 8（不是崩溃）。已知的稳定 FAIL：
  `idle-combo:1-尾巴完整`（面积波动判据）、`lick:1-尾巴完整` —— **这两项旧包就有，与改动无关**。

### ⑤ 装到桌面 —— 0 算力，人工确认

- 把产物挂到 **job** 上（`POST /v1/photo-avatar/steps`，`step=packFrameSequence`），
  否则前端拿不到 artifact。
- 用 `output/换上预览包.py <sessionId> <rev> <artifactUrl> <zipSha> --confirm`，
  它要动**三个**地方：
  1. 预览目录 `photo-avatar-frame-previews/<session>/<rev>/`；
  2. **安装目录** `pets/<petId>/assets/`（= `variants.manifest_path` 的父目录）；
  3. `photo_avatar_artifacts.sha256`。
- 🔴 **桌面真正加载的是安装目录，不是预览目录。** 只换预览目录 ⇒ 重启后看到的还是旧包。
  会话已到 `completed` 时必须走第 2 步。DB 里**没有**任何存帧数/哈希的列
  （`variants` 只有 5 列、`pets` 只有元数据）⇒ 除上面三处外没有别的要同步。
- 🔴 **这个脚本要跑 4~5 分钟**（拷 3 × 1149 个文件）。**必须后台跑 + 无缓冲**：
  ```
  ... python.exe -u output/换上预览包.py ... --confirm > output/换包日志.txt 2>&1
  ```
  否则会被工具的 120 秒超时 SIGTERM 掉，而且 **Python 的 stdout 是块缓冲、
  被杀时不 flush ⇒ 日志 0 字节**，看起来像「脚本秒退、什么都没干」——实际它已经改到一半。
- 🔴 **不许在脚本里 `rmtree` staging**：环境有**批量删除守卫**，一次删 > 50 个文件会被拦
  （实测 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":452,...}`）并终止进程。
  ⇒ staging 用**带时间戳的唯一目录名**（永不复用 = 永不需要删），收尾**挪进留档区**而不是删。
- ✅ 覆盖用 `shutil.copy2`（幂等），**不要用 `os.replace`**：中途被杀后 `os.replace` 会让
  staging 半空、预览目录半新半旧，重跑时清单比对直接堵死；`copy2` 重跑一遍即可。
- ✅ 验收用 `output/查换包状态.py <sessionId> <rev> <zipSha>`：它比
  **预览目录整树 sha == 安装目录整树 sha**、库 sha 一致、以及 `holdRange` 实际值。
  ⚠️（该脚本读 `actionId`，不是 `id`。）
- ⚠️ app 运行中改的文件，**要重启 app** 才看得到。

## 三、关键契约（改错一处就白跑）

### `holdRange` 的语义与失效条件

播放器（`frame-sequence-renderer.ts`）的判据只有一行：

```
switchAction:  if (loop && holdRange) this.holdHeld = true
currentFrame:  holdHeld ? 在 [lo, hi] 内循环 : index = (elapsed / duration) % frames.length
playMotion:    releasing = holdHeld && 同一动作 && !loop
```

**没有 `holdRange` 时**：

1. `carried`（`playMotion(..., {loop:true})`）退化成**整支无限循环** ⇒ 拖拽期间看不到「保持」；
2. `landed` 的 `releasing` 判据不成立 ⇒ 播放进度被**清零** ⇒ **从第 0 帧重播整支**，
   而不是续播「收回」尾段。

⇒ 用户看到的就是「点击后反馈过长」+「放下后没收回」。**这不是错值，是完全没有这个键。**

### 为什么不能自动标定

2026-09-14 在 05 的真实资产上试过三条线索，**互相矛盾**：

| 线索 | 给出 | 问题 |
|---|---|---|
| 速诊规则（宽度 ≤ 最窄×1.15 的连续段） | 退化成 `[0,120]` | 那是速诊，不是出厂值 |
| 设计比例（0.16..0.46）× 81 帧 | `[12,37]` | 与出厂 `[30,59]` 对不上 |
| 最直觉的「区间首尾相似」 | `IoU(f0030, f0059) = 0.41` | **不成立** |

⇒ `holdRange` 是**窗口**语义（窗口内来回循环），不是「循环点」语义；历史上就是人眼定稿的。
硬做自动标定 = 装一个「参数看着合法、体验随机」的拎起。
所以服务侧 `frames/hold_range.py` **只体检、一个字都不写进 manifest**。

### 中文否定句会把那个动作喂给模型

2026-09-19 教训：`details` 里写「画面里不做任何上升、离地、悬空、飘浮、托起的动作」，
**等于把「悬空」这个词直接喂给模型**。

⇒ `section` / `details` / `strict` 一律写**纯正向**描述
（写「始终正面朝向镜头」，**不要**写「不转身、不侧身」）；
禁止项只留在英文 `negative` 里。

### 视频时长锁死 12 秒

`VIDEO_DURATION = "12"`（常量，写进提示词文本的 `duration` 与它无关）。
**动作脚本的时间轴必须按 12 秒写**，否则模型会自己填满空档（= 加戏）。

## 四、已验证记录

### 2026-09-20：grab-release 第二次重出（时间轴改成 12 秒）

改了什么：

- 时间轴按 12 秒重写，**保持段占四分之三以上**（`1.0-10.2 秒`，9.2 秒）；
- `duration` 5 → 12；
- `section` / `details` / `strict` 里的中文否定句（「不转身、不侧身、不横向撑开」）
  全部改成正向描述；
- 英文 `negative` 补 `turning around / turning sideways / side view / changing orientation / rotating body`。

实测（`output/精修-量动作区间.py`，0 算力）：

| 项 | 上一版（5 秒脚本 + 12 秒视频） | 本版（12 秒脚本） |
|---|---|---|
| 帧数 | 287 | 289 |
| 头顶余量 y0 min | 82 | 74 |
| 触顶边帧 | 0/287 | 0/289 |
| 横向撑开 | **撑到 604~633**（crop box 只到 ~609，左右被裁） | 峰值同量级，但**稳定段在 562~568，框内** |
| 稳定段候选 | **没有**（姿态一路漂移） | **f0086 ~ f0205（120 帧 ≈ 5 秒）** |
| 末帧 vs 首帧 | 差 2px | 差 **1px** |

⇒ **「按 12 秒写脚本」解决了「模型加戏填空档」这个病根**，素材第一次出现了可用的稳定保持窗口。

对照靶子（内置 05 建国）：`grab-release` = 81 帧 + `holdRange: [30, 59]`（30 帧窗口 ≈ 1.26 秒）。
本版候选窗口 120 帧 ≈ 5 秒，**比内置的更宽裕**。

**人定窗口**：mp4 上量到 `f0086~f0205`；换算到**打包后的帧**（打包会跳掉 2 帧过渡）
是 **`f0104~f0169`（66 帧）**，写进 manifest 的 `holdRange: [104, 169]`。
服务侧 `hold_range.py` 自己挑的是 `f0220~f0286`（尾巴那个「没被拎起」的坐姿，IoU 0.908）——
**语义完全错**，再次印证「窗口只能人来定」。

### 2026-09-20：装进 7228（换包闭环跑通）

- 打包 sha `df8d9429…cc53e`（38 MB，1149 个文件）→ 挂 job → artifact `0f7d867b…0fa6`；
  artifact 与本地 zip **sha 一致**（打包确定性再次验证）。
- 换包结果：预览目录整树 sha == 安装目录整树 sha == `a4c577f8c0fcc340`；
  库 `photo_avatar_artifacts.sha256` = `df8d9429…`；两处 manifest 的
  `grab-release.holdRange` 都是 `[104, 169]`（287 帧）。
- 过程中踩的两个坑（已写进 ⑤）：**超时 SIGTERM + stdout 缓冲导致「假空输出」**、
  **批量删除守卫拦住 `rmtree(staging)`**。
