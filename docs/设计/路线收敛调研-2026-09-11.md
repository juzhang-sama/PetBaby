## 二、致命事实：schema 7 没有任何生产产出能力

| 环节 | 现状 | 证据 |
|---|---|---|
| Rust 解析/校验 schema 7 | ✅ 完整 | `runtime_assets/frame_sequence.rs:14-15` |
| Rust **产出** schema 7 | ❌ **无** | 写 schema 7 的代码只在 `#[cfg(test)]`（`frame_sequence.rs:492-495`） |
| Rust 资产 builder | ❌ **只有两个，都不是帧序列** | `runtime_assets/mod.rs:1-14` 仅 `photo_avatar_builder`(v5) + `pixel_avatar_builder`(v3) |
| Python 服务产帧序列 | ❌ **完全没有** | `services/appearance-generation/src` 搜 `frame-sequence-v1` / 多帧 / 视频 **零命中** |
| Python 服务的真实能力边界 | 只做「照片 → 单图」 | 像素 PNG（`pixel_avatar.py`）或 Live2D 纹理图集（`pipelines.py:495`） |
| 全仓库唯一 schema 7 生产者 | ⚠️ **手工脚本** | `scripts/build-frame-sequence-manifests.py:2,11`（注释自述"手动运行"）；内置 `public/builtin-pets/*/manifest.json` 即由此产出 |

**结论：04/05 的帧序列资产全是 POC 手工产物，生产管线根本不存在。**

## 三、要走视频，lk888 客户端必须先补能力

| 方法 | 端点 | 行 |

**缺口（走视频必须逐条解决）**：
1. **没有任何视频方法** —— 无文生视频/图生视频入口，唯一提交端点是图像 `:145-183`
2. **参数写死** —— `params={"size":"2048x2048","quality":"auto"}`（`:146`），无时长/帧率/首尾帧入参

4. **20 MiB 硬上限**（`:15,212,222`）→ 视频必然超
5. 禁止重定向（`:203-204`）、强制 HTTPS（`:197`）
6. 轮询只返回单一 `result_url`（`MediaState:49-90`），无多产物/多帧列表
7. 模型固定 `image_model = gpt-image-2`（`config.py:29,63`）—— 需接入 `models.json` 里已有的
   `doubao-seedance-1-5-pro` / `seedance-2-0-official` / `veo-3.1` / `sora-2`

## 五、⚠️ 顺序警告：先锁 pixel-v1 = 上传功能立刻归零

唯一替代路线（视频→帧序列）**生产管线还不存在**。所以：

| 方案 | 后果 |
|---|---|
| **A. 先建后锁** | 先把视频→抠像→帧序列生产管线建起来、能对新宠物跑通，再锁旧路线。**过渡期上传仍可用**（用旧路线） |
| **B. 先锁后建** | 立刻锁死全部旧路线，接受**一段时间内上传功能完全不可用**。好处：不会再有任何旧路线产物产生，目标纯粹 |

**建议 A。** 理由：锁的价值是"防止再产出旧路线资产"，而旧路线只在人主动上传时才产出；
在替代品没有之前先锁，只是把功能变成废的，并不加快收敛。
