# 桌面宠物项目产品与技术设计方案

> 文档状态：需求与总体设计已确认，等待进入实施规划  
> 目标平台：Windows 优先，保留 macOS 适配能力  
> 首版性质：内部原型与小范围测试版，不面向公开发布  
> 技术主线：Tauri + Rust + PixiJS/WebGL 2D 渲染

## 1. 产品定义

本项目首先是一款轻量、有生命感、不会打扰工作的桌面宠物，而不是以桌面宠物为外壳的 AI 助手。

用户可以带入自己的真实宠物、参考喜欢的宠物形象、通过少量维度创造一只宠物，或者直接领养内置宠物。宠物创建完成后常驻桌面，以克制的呼吸、眨眼和点击反馈形成陪伴感。

核心产品原则是：

> 云端负责创造，本地负责陪伴；常驻核心始终轻量，重型能力按需调用。

未来的 LLM、Agent、声音、主动养成和多宠互动，都围绕已经建立身份和关系的宠物扩展，不反过来主导桌宠核心。

## 2. 产品目标与成功标准

### 2.1 首要目标

1. 宠物能够稳定、自然地存在于 Windows 桌面，不抢焦点、不妨碍工作。
2. 宠物在长期常驻时保持较低的 CPU、内存和 GPU 占用。
3. 宠物即使只有正面坐姿，也能通过微动作形成最低限度的生命感。
4. 真实宠物照片生成的卡通分身应高度保留原宠特征，让主人能够辨认。
5. 宠物生成完成后，显示、互动、状态保存和切换必须完全离线可用。
6. 首版范围克制，但身份、形象、资产、行为和平台边界支持后续升级。

### 2.2 P1 需要验证的核心假设

- 用户是否愿意让宠物长期保持运行。
- 用户是否认为宠物有生命感，而不是一张桌面贴纸。
- 宠物是否会因为遮挡、误触或资源占用而被关闭。
- 真实宠物路线是否能在候选中提供至少一个主人认可的卡通分身。
- 一种统一画风、正面坐姿和少量互动能否支撑首轮体验验证。

## 3. 已确认的首版范围

### 3.1 平台与架构

- Windows 为第一优先平台。
- 从代码边界上保留 macOS 平台适配能力，但首版不承诺 macOS 可用。
- 桌面外壳采用 Tauri。
- 常驻核心采用 Rust。
- 2D 渲染采用 PixiJS/WebGL，并提供 Canvas 或静态显示降级能力。
- 云端多模态和图像生成 API 长期保留，通过供应商适配接口接入。

### 3.2 形象标准

- 首版宠物类型只支持猫和狗。
- 真实宠物首版只要求一张正面照片。
- 输出限制为统一招牌画风、正面或近正面、固定坐姿。
- 核心质量标准是保留原宠身份特征，而不是只生成一只可爱的同类宠物。
- 复杂动作和多角度形象后续通过补充三至五张照片解锁。
- 首版生成路线以“身份档案 + 单候选生成 + 确认/重新生成”为主（2026-08-04 定稿）。
- 为后续宠物专属身份适配器或 LoRA 等路线预留统一接口，但不在 P1 实现。

### 3.3 创建入口

首版同时提供三种入口（2026-08-05 定稿）：

1. **照片克隆（上传图片）**：上传一张宠物/参考图片，生成尽可能相似、主人可辨认的卡通形象。参考图片不再单独设置“特征重选”入口——上传动机统一理解为“越像越好”。
2. **直接领养**：从少量、高质量、辨识度明确的内置宠物中选择，一键上桌面。
3. **引导式创造**：把宠物身体提炼为固定部位（种类、体态、毛发轮廓、主色与花纹、脸部特征、标志性元素），每部分提供预定义选项，用户拼装生成。

三种入口最终都进入同一套宠物身份、形象生成和运行资产体系；引导式创造的部位结构为部件化/骨骼化运行时预留接口。

### 3.4 桌面行为

- P1 默认固定在用户放置的位置，不自主行走。
- 支持陪伴模式和桌面模式，默认使用陪伴模式。
- 宠物不抢焦点，透明区域鼠标穿透。
- 全屏、游戏或演示场景下自动隐藏。
- 单击头部或身体产生不同反馈。
- 长按拖动负责重新放置。
- 双击触发一个较明显但克制的特殊反应。
- 鼠标悬停默认不触发行为。
- 右键打开精简功能菜单。
- P1 完全静音。

### 3.5 多宠与离线

- P1 支持创建和保存多只宠物。
- 同一时间只激活并渲染一只宠物。
- 每只宠物独立保存身份、形象、状态、位置和未来 Agent 上下文。
- 多宠同屏作为后续亮点功能，不进入 P1。
- 宠物创建完成后，核心桌宠能力必须完全离线运行。

## 4. 阶段划分

### 4.1 P0：桌面运行验证

- 导入透明 PNG。
- 静态显示。
- 透明窗口与鼠标穿透。
- 拖拽、缩放、翻转和位置保存。
- 陪伴模式与实验性桌面模式。
- 托盘、隐藏和退出。
- 全屏避让。
- CPU、内存、GPU、DPI 和多显示器验证。

P0 是内部技术里程碑，允许宠物完全静态，不作为用户版本。

### 4.2 P1-A：生命感验证

- 使用预制的正面坐姿分层宠物。
- 实现呼吸、自然眨眼和点击反馈。
- 实现头部、身体命中区域。
- 实现拖拽、动作中断与恢复。
- 实现无惩罚的隐藏状态。
- 实现全屏自动隐藏和性能档位。
- 提供简化校准界面。

P1-A 的用户体验最低标准是：宠物不能只像一张贴纸。

### 4.3 P1-B：个性化创建验证

- 实现三种创建入口（照片克隆 / 直接领养 / 引导式创造）。
- 使用统一招牌画风生成正面坐姿候选。
- 实现单候选生成、自动检查和用户确认（不满意可重新生成）。
- 实现真实宠物身份一致性检查。
- 实现身份母版和本地运行资产编译。
- 支持保存多宠、单宠激活。
- 支持云端任务恢复和素材删除状态追踪。
- 确认生成后的宠物完全离线可用。

## 5. 总体架构

首版采用模块化单体，不提前建设通用插件平台，也不启动多个长期驻留的辅助进程。只有云端形象生成服务与桌面应用独立部署。

```text
Tauri 桌面应用
├─ 宠物窗口
│  ├─ PixiJS/WebGL 渲染器
│  ├─ 动画控制器
│  └─ 命中区域与交互输入
├─ 行为系统
│  ├─ 领域事件
│  ├─ 持续状态
│  ├─ 行为决策器
│  └─ 动作意图
├─ Rust 应用核心
│  ├─ 宠物资料库
│  ├─ 运行资产管理
│  ├─ 生成任务调度
│  ├─ 配置与安全存储
│  └─ 平台适配层
└─ 按需界面
   ├─ 创建流程
   ├─ 设置
   └─ 校准

云端形象生成服务
├─ 多模态身份理解
├─ 图像生成供应商适配器
├─ 身份与结构质量检查
└─ 素材生命周期管理
```

### 5.1 Rust 核心职责

- 管理窗口、托盘、全屏检测和未来开机启动。
- 保存宠物档案、持续状态和桌面配置。
- 加载、校验和迁移运行资产。
- 调度云端生成任务和恢复中断任务。
- 封装 Windows 与未来 macOS 的差异。
- 通过系统凭据库保存 API Key 等秘密。

### 5.2 渲染运行时职责

- 加载图片、图层和网格。
- 执行呼吸、眨眼、点击和拖拽反馈。
- 执行命中检测。
- 管理动作过渡、中断、降频与暂停。
- 根据可见性和运行档位调整渲染频率。

动画决策和逐帧更新留在渲染层，避免每一帧跨越 Tauri IPC。Rust 只接收具有业务意义的事件和状态快照。

### 5.3 平台适配边界

平台无关层只依赖统一语义：

```text
PlatformAdapter
├─ set_companion_mode
├─ set_desktop_mode
├─ set_click_through_regions
├─ detect_fullscreen
├─ enumerate_displays
├─ restore_window_position
└─ manage_tray
```

Windows 和 macOS 可以使用不同系统机制实现这些语义。不得让宠物身份、行为或渲染逻辑直接依赖 Win32。

## 6. 宠物身份与形象模型

形象系统必须区分三个概念：

- `IdentityProfile`：宠物是谁。
- `AppearanceRecipe`：这次要以什么方式呈现它。
- `RuntimeAsset`：桌面运行时如何高效显示和驱动它。

### 6.1 统一数据流

```text
创建输入
→ IdentityProfile
→ AppearanceRecipe
→ GenerationJob
→ AppearanceVariant
→ AssetCompiler
→ RuntimeAsset
```

### 6.2 IdentityProfile

身份档案描述不随画风、服装和动作改变的身份特征：

- 物种与体型。
- 脸型、耳朵、眼睛和鼻子。
- 毛色、毛发轮廓和花纹位置。
- 身体比例。
- 额头白斑、异色瞳、耳缺等标志性特征。
- 原始参考素材。
- 用户明确锁定、必须保留的特征。

真实宠物路线必须同时保留原图视觉锚点。结构化文字不能替代原始参考图。

### 6.3 AppearanceRecipe

形象配方描述一次生成目标：

```json
{
  "schemaVersion": 1,
  "styleId": "signature-cartoon-v1",
  "view": "front",
  "pose": "sitting",
  "background": "transparent",
  "accessories": [],
  "identityStrength": "high"
}
```

P1 只实现这一组值，但字段必须显式存在，不能散落为硬编码条件。

### 6.4 路线 B：首版生成策略

```text
照片质量检查
→ 主体分割
→ 多模态模型提取身份特征
→ 用户确认或修正关键特征
→ 生成一个候选
→ 自动结构质量检查
→ 用户确认（满意）或重新生成
→ 锁定身份母版
```

自动检查分为：

- 结构质量：多余肢体、五官异常、透明边缘损坏、主体裁切等。
- 身份一致性：脸型、毛色、花纹、眼睛、耳朵和标志性特征。

自动评分只用于淘汰明显失败结果和辅助排序。最终“是否是我的宠物”必须由用户确认。

### 6.5 路线 C：后续升级

用户补充三至五张多角度照片后，可以新增宠物专属身份约束：

```text
IdentityConstraint
├─ ReferenceConstraint
└─ TrainedIdentityAdapter
```

生成管线依赖统一接口，不关心底层使用多图特征融合、身份适配器、LoRA 或未来其他技术。P1 不训练宠物专属模型。

## 7. 运行资产编译

P1 采用“单张身份母版 + 少量局部生成资产 + 本地程序动画”。

```text
runtime-assets/<variantId>/
├─ manifest.json
├─ body.webp
├─ eyes-open.webp
├─ eyes-closed.webp
├─ thumbnail.webp
└─ calibration.json
```

`manifest.json` 至少记录：

- 资产格式版本。
- 画布尺寸和显示锚点。
- 图层、纹理及其校验值。
- 头部、身体等命中区域。
- 呼吸、眨眼和点击反馈参数。
- 最低运行时版本。

### 7.1 P1 动画方法

- 呼吸：对身体区域做极轻微的周期网格变形。
- 眨眼：切换睁眼和闭眼资产，间隔带随机性。
- 点击：头部或身体局部位移、缩放与弹性恢复。
- 拖拽：整体进入被抱起状态，落下后平滑恢复。

### 7.2 降级链

```text
完整分层动画
→ 部分局部动画
→ 单图程序变形
→ 静态显示
```

闭眼图生成失败时，可先使用母版眼部区域的局部压缩模拟眨眼。任何局部资产失败都不能导致宠物整体无法使用。

### 7.3 简化校准

自动结果异常时，用户可以：

- 移动或缩放眼睛区域。
- 调整头部和身体分界。
- 修改命中区域。
- 调整呼吸幅度。
- 在母版、闭眼图和动画预览之间切换。
- 重新生成闭眼资产。

自动结果正常时允许直接跳过。校准只修改运行参数，不修改身份母版。

## 8. 生命感与行为系统

### 8.1 分层模型

```text
用户操作与环境变化
→ 标准化领域事件
→ 持续状态与当前情境
→ 行为决策器
→ BehaviorIntent
→ 动画控制器
```

输入事件不直接指定动画。例如 `pet.head.clicked` 只表示头部被点击，行为决策器结合状态、冷却和上下文选择注视、眨眼、开心或安静回应。

### 8.2 持续状态

P1 只保留三个隐藏维度：

- `energy`：决定活跃度、休息倾向和眨眼频率。
- `mood`：决定短期反馈风格，并逐渐回归平静。
- `bond`：记录长期相处关系，缓慢增加少量反应变化。

默认采用无惩罚陪伴策略：

- 长时间未启动不降低亲近度。
- 不生病、不离家、不死亡。
- 不要求签到、喂食或清洁。
- 关闭期间不运行后台计时器。
- 再次启动时依据时间差进行一次温和状态恢复。

主动养成模式后置，并且必须由用户明确开启。

### 8.3 短期情境

```text
resting
alert
reacting
dragged
settling
quiet
hidden
```

短期情境描述当前运行状态，不属于永久身份。

### 8.4 动作优先级

1. 系统级：隐藏、暂停、全屏避让、退出。
2. 直接互动：拖拽、点击、双击。
3. 状态行为：困倦、休息、情绪反馈。
4. 环境微动作：呼吸、眨眼、轻微摆动。

高优先级动作可以中断低优先级动作。中断后平滑回到稳定姿态，不强制续播被中断的微动作。

### 8.5 防打扰规则

- 不抢焦点。
- 不主动弹出窗口、气泡或通知。
- 鼠标悬停不触发行为。
- 自动动作有随机间隔和冷却。
- 连续点击不会无限叠加反馈。
- 全屏或演示场景自动隐藏。
- 用户可以关闭状态驱动行为，切换为纯展示模式。
- P1 不播放声音。

### 8.6 未来 Agent 边界

未来 Agent 只能提交受约束的行为意图：

```text
BehaviorIntent {
  type: "express_happiness",
  intensity: 0.4,
  source: "agent",
  expiresAt: "..."
}
```

行为决策器可以接受、降级或拒绝意图。Agent 不得直接控制动画循环、绕过安静模式或任意修改 `bond` 等底层状态。

## 9. 多宠物模型

P1 使用以下边界：

```text
PetRepository
└─ 管理所有宠物档案

ActivePetSession
└─ P1 只允许一个活动会话

PetRuntimeInstance
└─ 单只宠物的渲染、状态和行为实例
```

不得把当前宠物实现为无法扩展的全局唯一对象。未来多宠同屏通过允许多个 `PetRuntimeInstance` 激活，并增加更高层的资源调度与互动协调器实现。

## 10. 本地存储与离线能力

建议采用：

- SQLite：保存宠物身份、形象变体、持续状态、设置、任务记录和版本信息。
- 独立资产目录：保存母版、图层、缩略图和运行纹理。
- 系统凭据库：保存 API Key 等秘密。

每只宠物使用稳定的 `petId` 隔离：

```text
Pet
├─ IdentityProfile
├─ AppearanceRecipe[]
├─ AppearanceVariant[]
├─ RuntimeAsset[]
├─ PersistentState
└─ DesktopPreferences
```

生成完成后，以下能力完全离线：

- 显示、呼吸、眨眼和点击反馈。
- 拖拽、缩放、窗口模式和全屏避让。
- 宠物切换。
- 持续状态演化。
- 配置、校准和行为状态保存。
- 应用重启后的状态恢复。

## 11. 云端任务、隐私与安全

### 11.1 云端任务状态

```text
queued
→ uploading
→ generating
→ reviewing
→ downloading
→ deleting_remote
→ completed
```

异常状态包括：

```text
failed
cancelled
remote_deletion_failed
```

任务中断后应可恢复，并避免重复扣费或产生无法追踪的云端副本。

### 11.2 默认隐私策略

- 原始照片和中间产物默认只在当前生成任务期间保留。
- 用户确认的结果下载到本地后，云端副本按策略删除。
- 删除失败必须可见，并允许重试。
- 失败样本不得默认用于训练或质量分析。
- 只有用户明确授权后，才可保留脱敏失败样本。
- 本地宠物资料默认不上传、不自动同步。
- 未来 Agent、声音和同步必须分别获得权限，不能复用形象生成授权。

### 11.3 安全要求

- 日志不记录照片内容、完整模型请求、API Key 或敏感路径。
- API Key 不写入 SQLite、普通配置文件或日志。
- 删除宠物时区分删除运行资产与删除全部身份资料。
- 网络参考图记录来源和用户使用确认。
- 明显知名角色、品牌形象或他人原创角色不默认执行一比一复制。

## 12. 轻量化设计

轻量化衡量的不只是安装包大小，还包括空闲占用、动画开销、恢复速度、资源释放和长时间趋势。

### 12.1 运行档位

| 档位 | 场景 | 渲染策略 |
|---|---|---|
| 活跃 | 点击、拖拽、明显反馈 | 临时提高帧率，动作结束后降档 |
| 陪伴 | 呼吸、眨眼、轻微动作 | 低帧率更新并使用插值 |
| 静止 | 无动作且无交互 | 停止连续渲染，事件唤醒 |
| 暂停 | 全屏、隐藏、休眠 | 停止渲染和行为调度 |
| 创建 | 生成、下载、资产编译 | 按需加载，任务结束后释放 |

参考策略：

- 点击和拖拽反馈临时使用 `30–60 FPS`。
- 呼吸等微动作使用约 `15–30 FPS`。
- 完全静止时停止连续渲染。
- 隐藏和全屏避让时暂停渲染。

具体帧率需要通过视觉实验调整，不能为追求指标而牺牲自然度。

### 12.2 初始性能预算

以下数值是 P0 工程目标，不是已验证承诺：

- 空闲 CPU 长期采样 `P95 <= 1%`。
- 微动画 CPU 长期采样 `P95 <= 3%`。
- 空闲私有内存目标 `<= 120 MB`，超过 `180 MB` 必须专项分析。
- 隐藏状态 CPU 接近 `0%`，不得持续轮询。
- 冷启动至宠物可见目标 `<= 3 秒`。
- 交互事件延迟目标 `< 50 ms`。
- 连续运行八小时内存不得持续单向增长。
- 生成和校准结束后，临时资源必须在可验证时间内释放。

测试时分别记录应用私有工作集、WebView2 子进程、GPU 进程、CPU、GPU、句柄数、线程数以及时间趋势。

### 12.3 资源保护

- 加载纹理前检查尺寸，拒绝异常超大图片。
- 根据显示尺寸生成适当分辨率的运行纹理，不常驻原始大图。
- 限制同一时间驻留的形象变体数量。
- 切换宠物后释放上一只宠物的纹理和动画实例。
- 创建、设置和校准窗口关闭后销毁并释放资源。
- 云端轮询采用指数退避。
- 日志设置大小上限和轮转。
- 状态保存采用节流，不按动画帧写入数据库。

## 13. 可靠性与错误降级

### 13.1 渲染降级

```text
WebGL 不可用
→ Canvas 渲染
→ 静态显示
→ 保留设置、导出和退出入口
```

### 13.2 资产降级

```text
局部动画资产异常
→ 禁用对应局部动作
→ 单图程序动画
→ 静态显示
```

### 13.3 云端失败

- 保留本地输入和任务记录。
- 显示可理解的失败阶段。
- 支持重试或重新选择候选。
- 不影响已有宠物。

### 13.4 本地存储失败

- 保留当前内存状态。
- 写入独立临时恢复快照。
- 明确提示存储异常。
- 不继续覆盖可能损坏的数据。

单只宠物资产损坏时应隔离该宠物，并允许切换其他宠物，不能导致整个应用无法启动。

## 14. Windows 技术预研矩阵

P0 至少覆盖：

- Windows 10 22H2。
- Windows 11 当前受支持版本。
- `100% / 125% / 150% / 200%` DPI。
- 单显示器与双显示器。
- 不同 DPI 的混合显示器。
- 主显示器切换、显示器断开和重新连接。
- 睡眠、唤醒和锁屏恢复。
- 全屏视频、演示和常见全屏应用。
- Windows Explorer 重启后的桌面模式恢复。

桌面模式依赖 Windows 桌面窗口层级，是 P0 的高风险能力。如果兼容性不足，P1 可将其标记为实验模式；默认陪伴模式必须稳定。

## 15. 开发里程碑与阶段闸门

### M0：技术探针

- Tauri 透明窗口。
- PixiJS 单图渲染。
- 宠物区域点击与透明区域穿透。
- 拖拽、缩放和位置恢复。
- 陪伴模式与实验性桌面模式。
- 多显示器、DPI 和全屏检测。
- 空闲与动画资源基线。

### M1：P0 桌宠运行时

- Rust 平台适配与本地存储。
- 托盘、隐藏、退出和基础设置。
- 静态透明 PNG 导入。
- 运行资产清单 v1。
- 性能档位和错误降级。
- Windows 兼容性验证。

### M2：P1-A 生命感

- 预制正面坐姿宠物。
- 呼吸、自然眨眼和点击反馈。
- 命中区域、拖拽与动作调度。
- `energy`、`mood`、`bond` 隐藏状态。
- 无惩罚陪伴策略。
- 简化校准界面。
- 长时间稳定性与体验测试。

### M3：生成链路实验

先在独立测试工具中验证：

- 多模态身份特征提取。
- 招牌画风定义。
- 四候选生成。
- 身份一致性与结构质量检查。
- 闭眼局部资产生成。
- 云端删除与任务恢复。
- 使用真实样本测试主人辨识度。

M3 通过模型对比实验选择供应商，架构不预先绑定具体模型。

### M4：P1-B 个性化创建

- 三种创建入口。
- 单候选确认（满意/重新生成）和有限局部调整。
- 身份母版确认。
- 运行资产编译和校准。
- 多宠保存、单宠激活。
- 生成后完全离线运行。

### 阶段闸门

```text
M0 窗口与性能可行
→ M1 常驻核心可靠
→ M2 生命感成立
→ M3 身份生成质量可接受
→ M4 完整小范围测试版
```

停止条件：

- M0 无法实现稳定穿透或满足合理资源预算时，暂停功能扩展并调整桌面技术路线。
- M2 测试者仍普遍认为宠物只是贴纸时，优先改进动画与互动。
- M3 多数真实宠物无法产生可辨识候选时，不把生成能力包装成已完成产品。

## 16. 验收标准

### 16.1 P0

- 透明 PNG 正确显示，无明显黑边或背景。
- 宠物区域可点击，透明区域穿透。
- 拖拽、缩放、翻转和位置保存可靠。
- 陪伴模式、桌面模式、隐藏和退出可用。
- 不抢焦点，不影响普通窗口输入。
- 全屏时按规则隐藏。
- DPI 或显示器变化后宠物不会永久丢失到屏幕外。
- 完成长时间资源测量，并达到预算或形成有证据的调整结论。
- 睡眠唤醒后仍可交互。

### 16.2 P1-A

- 呼吸可感知但不夸张。
- 眨眼间隔自然且非机械循环。
- 头部点击、身体点击和双击反馈可区分。
- 拖拽可中断动作，放下后平滑恢复。
- 隐藏状态跨重启恢复。
- 静止、隐藏和全屏时正确降档。
- 长时间运行不存在明显资源增长。
- 测试者不会因遮挡、误触或资源占用而倾向于关闭软件。

### 16.3 P1-B

- 三种创建入口都能形成合法的统一宠物档案（照片克隆 / 直接领养 / 引导式创造）。
- 真实宠物路线产生可判断候选，用户不满意可重新生成。
- 用户能够明确确认或拒绝身份相似性。
- 确认后的形象可编译成离线运行资产。
- 自动编译失败时能校准或降级。
- 多只宠物独立保存和切换，同时只激活一只。
- 断网后已有宠物完整可用。
- 云端素材删除状态可追踪，失败时可重试。
- 单个生成任务失败不破坏已有宠物数据。

形象质量不能仅以单一相似度分数验收。测试还应记录：

- 主人是否一眼认出。
- 哪些身份特征被保留或丢失。
- 候选中是否至少有一个可接受结果。
- 是否需要人工修改。
- 从上传到确认所需时间。
- 生成失败和资产降级比例。

## 17. 测试策略

- Rust 单元测试：状态迁移、资料库、任务恢复和版本迁移。
- TypeScript 单元测试：行为决策、动作优先级、冷却和降级。
- 契约测试：Tauri IPC、生成服务协议和资产清单。
- 渲染快照测试：图层、锚点、命中区域和降级显示。
- Windows 集成测试：透明窗口、穿透、托盘、全屏和 DPI。
- 长时间稳定性测试：资源趋势、睡眠唤醒和频繁切换宠物。
- 小范围体验测试：身份辨识度、生命感和干扰程度。

## 18. P1 明确非目标

P1 不包含：

- LLM 对话、Agent 和长期语义记忆。
- 声音、语音和音效。
- 主动养成模式。
- 自主行走和复杂动作。
- 多宠同屏和宠物之间的互动。
- 多角度生成和路线 C 专属模型训练。
- 多种画风、复杂服装系统或专业捏脸。
- 账号、云同步、支付、运营后台和公开发布体系。
- 完整本地图像生成模型。

这些能力只保留清晰的扩展边界，不在 P1 提前实现空框架。

## 19. 后续能力的扩展位置

| 后续能力 | 扩展位置 | 不应侵入的模块 |
|---|---|---|
| 新画风 | `AppearanceRecipe.styleId` 与生成策略 | 宠物身份、桌面窗口 |

| 宠物专属模型 | `IdentityConstraint` | 桌宠运行时 |

## 20. 已知风险与验证优先级

1. **Windows 透明窗口、动态穿透和桌面层级**：必须在 M0 最先实测。
2. **WebView2 常驻资源基线**：通过时间序列测量判断，而不是凭架构名称推断。
3. **单图卡通化身份保持**：通过真实宠物样本和主人确认验证，自动分数只能辅助。
4. **闭眼图与局部资产一致性**：必须具备程序动画和静态显示降级。
5. **桌面模式兼容性**：允许作为实验能力降级，但陪伴模式必须可靠。
6. **过度预留导致复杂化**：只定义稳定的数据所有权和接口，不提前开发插件平台、空服务和未使用框架。

## 21. 进入实施规划前仍需在计划中细化的事项

以下不是产品方向歧义，而是实施计划需要安排的技术验证项：

- Tauri 具体版本及 Windows 透明窗口相关插件或 Win32 补充实现。
- PixiJS 与 Canvas 降级的最小实现方式。
- SQLite 访问层、迁移机制和资产目录布局。
- `RuntimeAsset manifest v1` 的字段级 JSON Schema。
- Tauri IPC 命令和事件契约。
- Windows 基准设备与性能采样工具。
- M3 候选模型供应商、同输入对比样本和评分方法。
- 云端素材删除能力是否由供应商原生支持，或由自有中转服务保证。

这些事项应在实施计划或相应技术探针中用实验结果确定，不能在缺乏代码和实测的情况下假装已经完成选型。

## 22. 最终结论

本项目首阶段应聚焦于一只真正值得留在桌面上的宠物：它有稳定身份、自然微动作、克制互动和连续状态；不会抢焦点，不因断网失效，也不会因为未启用的重型功能长期占用资源。

首版以统一画风、正面坐姿和单宠激活控制范围，以身份档案、形象配方、运行资产、行为意图和平台适配等边界支撑后续升级。AI Agent 是重要的未来亮点，但只有当桌宠本身已经成立时，记忆、人格和对话才会增强依赖感，而不是掩盖基础体验不足。
