## 4. 三条创建链路的现状

### 4.1 上传图片

流程已经实现：创建 durable draft → 保存规范化私有源图 → 调用 provider → 持久化 job/candidate → 动态预览 → 命名 → finalization → 设置为当前宠物。

关键约束：

- API Key 只由应用本地存储和 UI 使用，严禁写入仓库、文档、日志或对话。
- 不要执行宽泛的 `SELECT * FROM state`；如需检查状态，只查询明确且非敏感的 key。
- 真实外部生成可能产生费用。再次提交 provider 前必须取得用户明确确认，并说明正常一次请求、异常网络最多三次重试。
- 上传初始 draft 已有直接可见的“放弃创建”入口；放弃会清理 placeholder pet/session/job/source。
- 候选和 finalization 支持响应丢失后的幂等恢复。

### 4.2 引导组合

正式包：`creation-content/composer/cat-cute-v1`。

- 3 个 body、4 个 ears、5 组 open/closed eyes、4 个 muzzle、4 个 tail、颜色/花纹及配套 mask。
- 共 51 张正式 1024×1024 RGBA PNG，外加严格 manifest。
- Rust 和 TypeScript 使用严格同构的版本化 pack 契约。
- recipe 保存、重开恢复、候选生成和 finalization 已完成。
- candidateReady 后配方不可再编辑；UI 会锁定前后导航。draft 状态仍允许返回修改。
- renderer 使用确定性离屏 Canvas 合成，最终通过单次 `copy + drawImage` 原子提交目标像素。

### 4.3 直接认领

正式目录包含 8 只离线猫：雾雾、橘子、团子、墨墨、云朵、栗子、芝麻、星星。

- 每只含 body、thumbnail、life-v1 motion profile；正式目录共 25 个文件。
- 同一 template 只允许一个长期有效认领事实。
- `creation_adoption_provenance` 持久保存来源版本和资产 hash；旧版本重试不依赖当前 catalog。
- 单模板普通文件缺失、hash/PNG/profile 内容损坏只禁用该卡；路径逃逸、reparse、文件身份/TOCTOU、bounded-read 安全错误仍使整个 catalog fail-closed。
- 两个独立 SQLite 连接的并发认领会通过唯一约束收敛到同一 pet/session。
- 认领卡片支持 roving tabindex、Arrow/Home/End、焦点保留、失败刷新和 reduced-motion。

## 5. 不得破坏的核心安全协议

### 5.1 候选发布

composer 和 adoption 共用参数化发布核心，但使用不同 namespace 的 intent 文件。

- 阶段为 immutable `reserved → owned → complete`。
- 每个阶段只通过 `NO-REPLACE + MOVEFILE_WRITE_THROUGH` 发布。
- 所有阶段句柄保持到 commit/rollback。
- 恢复只接受连续单调前缀，并核对 session、stage、hash、目录与文件 FileId。
- legacy、未知 sentinel、阶段缺口、身份不符或跨 record 不一致均保留并 warning，禁止误删未知对象。
- 清理严格按 `complete → owned → reserved` 逆序，首错停止，确保崩溃后始终剩合法前缀。
- staging、candidate 和 JSON/PNG 读取都有数量、metadata 和字节上限，禁止无界读取。

### 5.2 路径与文件系统

- 只接受由可信根产生的私有 `ContentRoot`，不能把任意 `Path` 传入 pack 校验。
- 所有组件、最终文件和资源在使用前重新解析并验证 containment、文件类型、reparse 和身份。
- Windows 发布使用句柄/FileId 与 extended-length path；不要退回“校验 PathBuf 后再裸路径写入”的实现。
- `runtime_assets/motion_profile.rs` 已支持超过旧 Win32 260 字符限制的原子写入。

### 5.3 哈希与换行

受哈希保护的 JSON 必须保持字节稳定：

- `.gitattributes` 固定 Live2D manifest/cdi3/model3 为 LF。
- `.gitattributes` 固定 `apps/desktop/public/creation-content/**/*.json` 为 LF。
- 不要删除 `tauri-resource-bundle.test.ts` 中的 Windows checkout 契约。
- 读取 Rust 源码做静态契约的测试必须先把 CRLF 规范为 LF，不能依赖工作树换行。

## 6. UI 与交互架构

- 设置页提供“上传图片 / 引导组合 / 直接认领”三张语义入口卡。
- durable draft 冲突会提供继续、取消或确认放弃的裁决，不会静默删除其他创建方法的草稿。
- 三条链路共享 `CreationPageActivity`，所有外层用户 mutation 串行化；路由切换会等待 settlement。
- busy 状态会同步按钮、tabs、back、`aria-busy` 和 inert 行为。
- adoption 目录使用稳定 DOM 节点和最小 reorder，跨 busy 捕获/恢复焦点；外部元素获得焦点时不会抢回。
- reduced-motion 会真实停止并恢复 idle/RAF，而不是只改变 CSS。
- 窄屏断点与键盘/ARIA 契约已有测试覆盖。

## 8. 已修复的高风险问题

- `pattern.image` 在 Rust 中曾把缺失字段当作 null；现要求字段必须存在，显式 null 才表示无图案。
- Canvas 最终提交曾先 clear，失败会破坏旧预览；现为单次原子 copy draw。
- composer 尾巴平切、耳根硬边、绿/橄榄 fringe、眼睛色键残留均已重做并固化像素契约。
- candidate 发布曾有 PathBuf TOCTOU、intent replacement race、cleanup gap 和 partial staging orphan；已改为 immutable phase + handle/FileId 协议。
- adoption catalog 曾被 ghost/cross-owned facts、provenance hash、runtime path 和 Windows 分隔符问题绕过；均已加入严格事实投影。
- 单个 adoption 模板损坏曾拖垮整个 catalog；现按显式 Security/Content/FileIo 类型分层。
- Vite 曾未打包 `settings.html`；现为双入口。
- Tauri resource glob 曾压平 `creation-content` 层级；现为目录映射。
- Live2D 和 creation-content JSON 曾受 Windows CRLF 影响导致 manifest hash mismatch；已由 `.gitattributes` 和回归测试固定 LF。
- composer 恢复文案、candidateReady 伪编辑入口、adoption 焦点时序、共享路由 mutation、reduced-motion 均已修复。

## 9. 当前已知边界

- 真实 GUI 没有故意制造 provider 外部失败和编译失败；对应恢复路径已有自动化测试。
- non-Windows 的安全发布实现生产态明确 fail-closed；Windows 已实测，其他 target 的编译边界应由 CI 验证。
- API Key 属于本地敏感状态，不要在新对话中要求输出、复制、查询或写入文档。
- 真实 provider 调用和任何宠物/草稿删除都需要用户在动作发生前再次明确确认。
- 正式 `creation-content` 测试应使用临时复制或 test fixture；不得为了故障注入修改正式素材。
- 不要删除或改写 Task15 已提交证据来“让指标更好”；分析规则和阈值已经冻结并独立复算通过。
