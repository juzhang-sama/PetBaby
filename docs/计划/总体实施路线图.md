# 桌面宠物项目总体实施路线图

> **For agentic workers:** 每个阶段开始实施前，必须使用 `subagent-driven-development`（推荐）或 `executing-plans` 技能执行该阶段的详细计划；不得跨过阶段闸门提前实现后续功能。

**目标：** 按 M0 至 M4 的顺序，将已确认的桌面宠物设计实现为 Windows 优先、生成后离线可用的小范围测试版。

**架构：** 桌面应用采用 Tauri 2 + Rust 常驻核心，宠物运行时采用独立的 TypeScript + PixiJS 8 入口。平台能力、宠物领域模型、运行资产、行为系统和云端生成以稳定契约隔离；先验证 Windows 高风险能力，再逐步冻结后续实现。

**技术栈：** Windows 10/11、Tauri 2、Rust stable、TypeScript、Vite、PixiJS 8、Vitest、SQLite、PowerShell 性能采样、云端多模态与图像生成 API。

## 全局约束

- Windows 为第一优先平台；代码边界保留 macOS 适配能力，但 P1 不承诺 macOS 可用。
- 常驻核心轻量，重型能力按需调用；生成、设置和校准窗口关闭后释放资源。
- 云端负责创造，本地负责陪伴；生成完成后的显示、动画、互动、状态和切换必须离线可用。
- P1 只支持猫和狗、统一招牌画风、正面或近正面、固定坐姿。
- P1 支持保存多宠，但同一时间只激活一只。
- P1 不包含 LLM/Agent、声音、主动养成、自主行走、多宠同屏、多画风、账号、同步、支付和公开发布体系。
- 所有领域数据和运行资产使用版本字段；不得用首版硬编码替代身份、配方、变体和运行资产边界。
- 采用 TDD、阶段内频繁提交；任何阶段未通过闸门，不得将其能力描述为已完成。
- 当前工作区不是 Git 仓库。执行 M0 时在 `desktop-pet/` 新建独立仓库；不得把 `outputs/` 和 `work/` 直接变成产品仓库。

## 1. 为什么拆成五个阶段计划

已确认规格包含五个具有不同失败模式的子系统：

| 阶段 | 要回答的问题 | 失败时的处理 |
|---|---|---|
| M0 技术探针 | Tauri/WebView2 能否稳定满足 Windows 桌宠窗口语义与资源基线 | 调整 Windows 窗口实现或桌面技术路线 |
| M1 P0 运行时 | 常驻核心、存储、资产清单和平台适配是否可靠 | 修复运行时，不进入动画体验开发 |
| M2 P1-A 生命感 | 微动作、状态与交互是否让宠物摆脱“贴纸感” | 改进资产和行为，不接入生成流程 |
| M3 生成实验 | 单张正面图能否产出主人可辨认的统一画风候选 | 更换模型、提示策略或身份约束方式 |
| M4 P1-B 创建闭环 | 四入口、单候选确认与重新生成、校准、多宠与离线能否形成完整体验 | 修复对应创建或资产编译环节 |

M1 至 M4 的详细实施计划必须读取上一个阶段的技术结论后再编写。现在只冻结跨阶段契约和验收闸门，不猜测尚未实测的 Win32、模型供应商或素材删除能力。

## 3. 跨阶段目录边界

预计最终仓库按职责组织，而不是把所有 Rust、前端或 API 代码堆在单个目录：

```text
desktop-pet/
├─ apps/
│  └─ desktop/
│     ├─ src/
│     │  ├─ runtime/                 # 无 React 的轻量宠物入口
│     │  ├─ behavior/                # 事件、状态、决策和意图
│     │  ├─ assets/                  # 运行资产解析与渲染适配
│     │  ├─ calibration/             # P1-A 按需校准界面
│     │  └─ creation/                # P1-B 按需创建界面
│     └─ src-tauri/
│        └─ src/
│           ├─ platform/             # Windows/macOS 适配边界
│           ├─ pets/                 # 宠物资料库与活动会话
│           ├─ runtime_assets/       # 清单校验、加载与迁移
│           ├─ generation/           # 按需云端任务调度
│           └─ storage/              # SQLite、资产目录、恢复快照
├─ packages/
│  ├─ contracts/                     # TS/JSON Schema 契约源
│  └─ test-assets/                   # 无隐私风险的测试资产
├─ services/
│  └─ appearance-generation/         # M3 结论通过后才创建
├─ scripts/
└─ docs/
```

M0 为减少脚手架噪声，先在 `apps/desktop` 和 `scripts` 中实现技术探针。只有某个边界在 M0 通过后，才迁入上述稳定目录。

## 4. 冻结的跨阶段契约

以下概念名称在后续计划中保持一致：

```ts
type PetId = string;
type VariantId = string;
type WindowMode = "companion" | "desktop";
type RenderTier = "active" | "companion" | "still" | "paused";
type AssetType = "single-image" | "layered-v1";

interface IdentityProfile {
  schemaVersion: 1;
  petId: PetId;
  species: "cat" | "dog";
  identityMode: "real_pet" | "reference" | "guided" | "adopted";
  referenceAssetIds: string[];
  lockedTraits: string[];
}

interface AppearanceRecipe {
  schemaVersion: 1;
  styleId: "signature-cartoon-v1";
  view: "front";
  pose: "sitting";
  background: "transparent";
  identityStrength: "high";
}

interface BehaviorIntent {
  type: string;
  intensity: number;
  source: "runtime" | "user" | "agent";
  expiresAt: string;
}
```

M1 负责把这些接口扩展成字段级 JSON Schema 和 Rust 类型。M0 不提前实现完整宠物领域模型。

## 5. M0：Windows 桌宠技术探针

**详细计划：** `outputs/桌面宠物M0技术探针实施计划.md`

**交付结果：** 一个只导入测试透明 PNG 的 Windows 探针程序，以及带实测证据的窗口、DPI、全屏、桌面模式和性能结论。

**必须验证：**

- 透明窗口与透明背景正确显示。
- 宠物区域可点击，透明区域把点击交给后方窗口。
- 拖拽、缩放、翻转和位置恢复。
- 默认陪伴模式不抢焦点。
- 实验性桌面模式能进入、退出，并记录 Explorer 重启表现。
- 全屏检测和自动隐藏。
- 单/双显示器、混合 DPI、睡眠唤醒。
- 空闲、交互、隐藏三种状态的资源趋势。

**闸门：**

- 默认陪伴模式稳定且不抢焦点。
- 动态穿透策略有可复现实测结论。
- 桌面模式若不可靠，明确降级为实验功能，不阻止 M1。
- 资源基线达到设计预算，或产生经证据支持的新预算。
- 输出 M0 技术决策记录，冻结 M1 的 `PlatformAdapter` 实现策略。

## 6. M1：P0 桌宠运行时

M0 通过后编写 `M1-P0运行时实施计划.md`，不得提前开始。

**预计任务边界：**

1. 将 M0 的 Windows 探针收敛成 `PlatformAdapter`。
2. 定义 `RuntimeAsset manifest v1` JSON Schema 和 Rust/TS 类型。
3. 引入 SQLite 迁移、资产目录和恢复快照。
4. 实现 `PetRepository`、`ActivePetSession` 和单一 `PetRuntimeInstance`。
5. 实现透明 PNG 导入、尺寸限制、纹理派生和校验值。
6. 实现托盘、隐藏、退出、模式切换和设置窗口生命周期。
7. 实现渲染降级、资产隔离和崩溃恢复。
8. 建立 Windows 集成测试与性能回归脚本。

**闸门：** P0 全部验收项通过；单宠资产损坏不阻塞应用启动；断网不影响本地宠物；连续八小时无单向内存增长。

## 7. M2：P1-A 生命感

M1 通过后编写 `M2-P1A生命感实施计划.md`。

**预计任务边界：**

1. 建立领域事件、短期情境、动作优先级和冷却规则。
2. 实现 `energy`、`mood`、`bond` 与无惩罚 `CompanionPolicy`。
3. 引入预制正面坐姿分层宠物资产。
4. 实现呼吸、随机眨眼、头部/身体点击和双击反馈。
5. 实现拖拽中断、抱起、落地和动作恢复。
6. 实现 `active/companion/still/paused` 渲染档位。
7. 实现按需打开的简化校准窗口。
8. 完成体验测试、长时间稳定性和“贴纸感”闸门评估。

**闸门：** 测试者能感知生命感；互动不会高频打扰；状态跨重启温和恢复；P1-A 性能预算通过。

## 8. M3：形象生成链路实验

M2 通过后编写 `M3生成链路实验计划.md`。此阶段是独立实验工具，不直接进入桌宠主流程。

**预计任务边界：**

1. 定义经用户同意的真实宠物测试集和评估表。
2. 定义招牌画风视觉约束与正面坐姿输出规范。
3. 对比至少两种可替换的云端多模态/图像生成供应商。
4. 实现身份特征提取和用户锁定特征结构。
5. 实现四候选生成、结构质量过滤和身份辅助排序。
6. 实验闭眼局部编辑与透明背景稳定性。
7. 验证任务幂等、断点恢复、供应商删除能力和自有中转边界。
8. 以主人确认而非单一相似度分数作阶段结论。

**闸门：** 多数样本至少产生一个主人可接受候选；失败类型可分类；供应商数据生命周期可被产品明确表达；否则不进入 M4。

## 9. M4：P1-B 个性化创建闭环

M3 通过后编写 `M4-P1B创建闭环实施计划.md`。

**预计任务边界：**

1. 建立统一 `IdentityProfile`、`AppearanceRecipe`、`GenerationJob`、`AppearanceVariant` 和 `RuntimeAsset` 持久化。
2. 实现真实宠物、参考图片、引导创建和内置领养四入口。
3. 实现单候选确认（满意/重新生成/放弃）、身份确认和有限特征修改。
4. 实现云端任务恢复、幂等、取消、下载和远端删除重试。
5. 实现身份母版、闭眼资产和本地程序动画参数编译。
6. 自动编译失败时进入校准或单图降级。
7. 实现多宠保存、切换和单宠激活。
8. 完成断网、隐私、资产损坏和小范围体验验收。

**闸门：** P1-B 全部验收项通过；用户能确认或拒绝身份；生成服务失败不破坏已有宠物；生成完成后完全离线可用。

## 10. 每阶段统一验证要求

每份阶段计划都必须包含：

- 先写失败测试，再写最小实现。
- 精确文件路径、接口签名、测试命令和预期结果。
- Rust 单元测试、TypeScript 单元测试和 IPC/Schema 契约测试。
- 与阶段风险相称的 Windows 人工验收步骤。
- 性能采样而非单点截图。
- 提交前 `npm test`、`npm run typecheck`、`cargo test`、`cargo clippy -- -D warnings` 和 `npm run tauri build -- --debug`。
- 中文阶段结论文档，区分“通过”“实验性”“未通过”和“未测试”。
- 阶段末独立代码审查和规格覆盖检查。

## 12. 路线图完成条件

路线图在 M4 闸门通过后完成。完成结论必须同时包含：

- 可运行的 Windows 小范围测试版。
- P0、P1-A 和 P1-B 的验收证据。
- 性能、兼容性和长时间运行记录。
- 真实宠物身份辨识度测试结果。
- 云端素材生命周期与失败恢复结果。
- 明确列出的实验性能力和未解决风险。

在这些证据产生前，不开始 Agent、声音、主动养成、自主行走或多宠同屏的实施规划。
